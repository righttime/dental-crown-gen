## Research question + answer

**RQ:** Given an *image* of a 3D object, or a *partial* 3D scan, or a set of *2D part masks*, can we generate a *compositional* 3D object made of *K complete, semantically meaningful parts* where (1) the parts *fit together* cohesively (no intersections, no gaps), (2) the *number* of parts is *discovered* automatically (not fixed a priori), (3) the *generation* is *fast* enough for interactive use (vs PartGen's 5-min per object), and (4) the *model* is *unified* across the three input scenarios (image, partial 3D, masks)?

**Answer (AutoPartGen's):** Yes — by exploiting a *newly discovered* property of the 3DShape2VecSet latent space: it is *inherently compositional*. Specifically, 𝒛 = 𝒛⁽¹⁾ ⊕ 𝒛⁽²⁾ decodes to 𝒙 = 𝒙⁽¹⁾ ∪ 𝒙⁽²⁾ — i.e., the *concatenation* of two part-codes decodes to the *union* of the two part-surfaces. This *single property* enables a *simple but powerful* autoregressive architecture: (1) encode the previous parts, re-encode through the VAE encoder E to get a *fused* code 𝒛⁽¹⁾∪⋯∪𝒛⁽ᵏ⁻¹⁾, (2) concatenate with the overall object code 𝒛̃ and optional image conditioning, (3) a DiT (2048×24) denoises the next part code 𝒛⁽ᵏ⁾ from Gaussian noise via flow matching, (4) decode 𝒛⁽ᵏ⁾ to the next part 𝒙⁽ᵏ⁾, (5) loop until the model emits an `[EoT]` empty-shape token. The *result*: a *single* model that handles all three scenarios, generates a *variable* number of parts *automatically*, is *fast* (~seconds, not minutes, because the DiT operates on a *small* latent not on 3D space), and is *unified* (one model, one training pipeline, one inference loop). The SOTA result on PartObjaverse-Tiny (CD 0.047 / 0.012 — *better* than HoloPart *and* PartGen despite using *less* input information, no 3D masks) is the *direct* evidence that the autoregressive compositional latent is the *right* representation.

## Method

### 3DShape2VecSet compositionality (Sec 3.1, the discovery)

The *single most important* contribution: AutoPartGen *discovers* (and *operationalizes*) the compositionality of the 3DShape2VecSet latent. The original 3DShape2VecSet (Zhang et al. 2023) is an *encoder-decoder* pair (E, D) where E maps N surface points P = {p₁, ..., p_N} ∼ x to a sequence of M latent tokens 𝒛 = (z₁, ..., z_M) via cross-attention from learnable queries to P (FPS-subsampled), and D maps (𝒛, query point q) → SDF logit. The *new* observation: **the concatenation 𝒛 = 𝒛⁽¹⁾ ⊕ 𝒛⁽²⁾ of two codes 𝒛⁽¹⁾, 𝒛⁽²⁾ decodes to the union 𝒙 = 𝒙⁽¹⁾ ∪ 𝒙⁽²⁾ of the two corresponding surfaces** (the *empirical* property, demonstrated on the paper's Fig 3). This *single property* enables part-3D-generation via code-level composition, *without* requiring the decoder to learn how to *blend* parts (the *traditional* compositionality challenge in NeRF / SDF / Gaussian Splatting).

### Autoregressive part generation (Sec 3.2, Sec 3.3, the architecture)

The *core* architecture: a *single* DiT (Peebles & Xie 2023, the *standard* 2024-2025 3D-gen DiT) with width 2048, 24 layers, that denoises the *next* part code 𝒛⁽ᵏ⁾ given (1) the *overall* object code 𝒛̃, (2) the *fused* code of previous parts 𝒛⁽¹⁾∪⋯∪𝒛⁽ᵏ⁻¹⁾ (computed by re-encoding the previous parts through E, the *engineering* trick for code-level fusion), and (3) optional image conditioning y = (I, J⁽ᵏ⁾) (where J⁽ᵏ⁾ = I ⊙ M⁽ᵏ⁾ is the part-masked image, encoded via DINOv2, the *de facto* 2024-2025 image encoder). The DiT predicts the *velocity field* v̂(t, 𝒛_t | 𝒛̃, 𝒛⁽¹⁾∪⋯∪𝒛⁽ᵏ⁻¹⁾, y) of a *rectified flow* (the *same* flow-matching formulation as HoloPart 094 + TripoSG + CLAY, the *de facto* 2024-2025 latent-diffusion objective), trained with:
- AdamW, LR=1e-4, 500K iterations on 256 H100 GPUs (4 days wall-clock)
- Random conditioning dropout: image dropped with p=0.05, geometry dropped with p=0.05, both dropped with p=0.05 (for CFG)
- Default CFG: w_img=7, w_geom=4 (modulating the image-vs-geometry conditioning strength)

The generation process is a *loop*: at each step k, sample 𝒛⁽ᵏ⁾ from p(𝒛⁽ᵏ⁾ | 𝒛̃, 𝒛⁽¹⁾∪⋯∪𝒛⁽ᵏ⁻¹⁾, y) via flow-matching, decode 𝒛⁽ᵏ⁾ to 𝒙⁽ᵏ⁾ via D (the 3DShape2VecSet decoder), fuse 𝒛⁽ᵏ⁾ into 𝒛⁽¹⁾∪⋯∪𝒛⁽ᵏ⁾ via E, and *continue* until the model emits the `[EoT]` (End-of-Tokens) empty-shape token (the *learned* stop signal, the *killer* mechanism for variable-part-count). In the *masks-to-parts* scenario, the generation *stops* when all input masks have been processed (i.e., the number of parts K is *fixed* by the user, but the model still generates *each* part autoregressively).

### Three scenarios (Sec 3, unified model)

AutoPartGen handles *three* scenarios with a *single* model:
1. **object-to-parts**: input is the 3D object 𝒙, output is a decomposition 𝒙⁽¹⁾, ..., 𝒙⁽ᴷ⁾. The overall code 𝒛̃ = E(sample_N 𝒙̂) is computed from the input 3D object.
2. **image-to-parts**: input is a single image I, output is both the *full* 3D object 𝒙 and its decomposition. The overall code 𝒛̃ is *self-predicted* via 𝒛̃ ∼ p(𝒛 | I) (a *separate* diffusion process at the *object* level, trained jointly with the part-level diffusion — the *practical* mechanism for image-conditioned part-3D).
3. **masks-to-parts**: input is image I + K 2D part masks M⁽¹⁾, ..., M⁽ᴷ⁾, output is K complete 3D parts matching the masks. The masks provide *which-part-to-generate-next* guidance (the *killer* UX for interactive editing).

The *unified* training: a *single* model is trained on *all three* scenarios with the *random* conditioning dropout, so the model *learns* to use any subset of the available evidence at inference time. The *result*: a *single* 24-layer DiT that handles all three tasks, vs PartGen's *three separate* multi-view diffusion models (one per scenario) and HoloPart's *two-stage* (SAMPart3D + HoloPart) pipeline.

### Data pipeline (Sec 4.1, the practical H5)

The training data: ~1.8M Objaverse-XL 3D assets → filtered to ~300K *high-quality* assets → ~2M individual parts. The filtering: cap mesh count at 15 (iteratively merge meshes from the bottom up if exceeded), ensure all assets are licensed for AI training, all in glTF/GLB format with hierarchical structure. For each part, compute the *truncated signed distance* in a normalized space (for VAE training), and render *multiple views* (for image-conditioned training).

### Architecture details (Sec 4.1 + Supp)

- **VAE encoder**: 32K input points (FPS-subsampled to M tokens), point coordinates + normals as features (vs the original 3DShape2VecSet's 16K points, the *2×* increase for *better* detail), 24 transformer blocks (the *standard* 3DShape2VecSet + CLAY architecture)
- **DiT**: width 2048, depth 24 layers, the *standard* 2024-2025 3D-gen DiT (same as CLAY, TripoSG, HoloPart)
- **Image encoder**: DINOv2 (the *de facto* 2024-2025 image encoder for 3D-gen), applied to *both* the full image I and the part-masked image J⁽ᵏ⁾ = I ⊙ M⁽ᵏ⁾, features concatenated + small MLP to match DiT input
- **Flow matching**: rectified flow with linear interpolation forward process 𝒛_t = (1-t)·𝒛_0 + t·ε, t ∈ [0, 1], flow-matching loss L = ‖v_θ(𝒛_t, t, c) − (ε − 𝒛_0)‖²₂ (the *standard* flow-matching formulation)
- **Inference**: ~20-50 denoising steps per part (via DPM++ / Euler / FlowMatch schedulers), ~2-10s per part on 1× A100, total ~30-60s for a 5-part object (the *massive* speed-up vs PartGen's 5-min multi-view pipeline)

|---|---|---|---|---|---|---|---|

| PartGen | ✗ | 0.614 | 0.812 | 0.121 | 0.779 | 0.921 | 0.033 |

**Headline gains**:
- **CD reduction vs HoloPart**: 0.065 → 0.047 on parts (1.4× reduction), 0.018 → 0.012 on whole object (1.5× reduction)
- **CD reduction vs PartGen**: 0.121 → 0.047 on parts (2.6× reduction), 0.033 → 0.012 on whole object (2.8× reduction)
- **IoU + F-Score gains**: +0.007 IoU, +0.025 F-Score on parts vs HoloPart; +0.051 IoU, +0.049 F-Score on parts vs PartGen
- **No 3D mask required**: AutoPartGen uses *only* the partial 3D mesh + 2D masks (not the 3D part mask that HoloPart requires), making it *more practical* for clinical use where 3D part masks are *not* available
- **Best of all three metrics across both part-level and whole-object evaluation**

### Ablations (Sec 4.4 + Fig 8)

- **Autoregressive conditioning** (Fig 8a): removing the previous-parts conditioning 𝒛⁽¹⁾∪⋯∪𝒛⁽ᵏ⁻¹⁾ causes parts to *overlap and intersect* (the *qualitative* finding, no number reported), demonstrating the *critical* role of the autoregressive context for *part-coherence*
- **Image guidance w_img** (Fig 8b): increasing w_img encourages the model to follow the *image* masks more closely (higher fidelity to the input image, at the cost of *part-diversity*)
- **Geometry guidance w_geom** (Fig 8b): increasing w_geom biases the model towards its *learned prior* of plausible part structures (higher *part-naturalness*, at the cost of *image-fidelity*)
- The two CFG scales (w_img=7, w_geom=4 default) provide a *practical* trade-off knob for *image-fidelity vs part-naturalness*

### Applications (Sec 4.5, Fig 1)

- **3D scene generation**: generate an *isometric view* of a small scene → AutoPartGen produces *individual* scene objects (chairs, clocks, plants, tables) as decomposable parts. The *killer* application for *scene-level* 3D generation with *object-level editability*.
- **City generation**: text → 2D tile image (via text-to-image generator) → AutoPartGen generates *per-tile* 3D structures → assemble into a cityscape (via the *SynCity*-style pipeline, drawing on Engstler et al. 2025). The *killer* application for *scalable* large-scene generation.

## Connections to H1-H5

**H1 (2-stage VAE + DDM > 1-stage) — STRONG SUPPORT, slightly different formulation.** AutoPartGen is *technically* a 2-stage pipeline (Stage 1: 3DShape2VecSet VAE encoding/decoding + Stage 2: DiT latent diffusion on top), the *same* 2-stage pattern as HoloPart 094 + CLAY + TripoSG + CLAY. The *key difference* from HoloPart: AutoPartGen *unifies* the segmentation + completion stages into a *single* autoregressive diffusion (vs HoloPart's separate SAMPart3D + HoloPart diffusion). For v0 sub-task 4 (crown generation from prep scan), the *practical* implication: a *single* model can *both* discover the parts AND generate them (no need for a separate segmentation network), the *engineering* simplification. **The H1 support is *partial* — AutoPartGen *is* 2-stage VAE+DDM, but the *segmentation+generation* unification challenges the *HoloPart* formulation of "segmentation is a separate stage".**

**H2 (latent diffusion > direct) — STRONG SUPPORT, even stronger than HoloPart.** AutoPartGen is *literally* a latent-flow model: 3DShape2VecSet VAE → flow-matching DiT in the latent → VAE decoder. The +64% F-Score gain (0.861 vs 0.232 for PatchComplete from paper 094) over *direct* 3D completion is the *strongest* H2 evidence in the 3D-part-generation literature. The *additional* gain over HoloPart (0.861 vs 0.836 F-Score, +0.025) is the *evidence* that the *autoregressive compositional* approach in the *same* latent space is *superior* to the *non-autoregressive amodal-completion* approach in the *same* latent space. For v0 sub-task 4, the *architectural template* is *the same as HoloPart* (VAE + DiT), the *additional* benefit is the *autoregressive* structure for *part-coherence* + *variable-part-count* discovery.

**H3 (conditioning on adjacent+opposing teeth) — STRONG SUPPORT, the *killer* mechanism is the *fused* code 𝒛⁽¹⁾∪⋯∪𝒛⁽ᵏ⁻¹⁾.** The *entire* AutoPartGen architecture is *literally* a *conditioning* mechanism on (1) the *previous parts* (via the *fused* code), (2) the *overall* object's code 𝒛̃, and (3) the image I + part-masked image J⁽ᵏ⁾. The *fused* code 𝒛⁽¹⁾∪⋯∪𝒛⁽ᵏ⁻¹⁾ = E(∪ⱼ₌₁ᵏ⁻¹ sample_N D(·|𝒛⁽ʲ⁾)) is the *killer* mechanism for H3: the *adjacent* part (the previously generated part 𝒙⁽ᵏ⁻¹⁾) is *explicitly* re-encoded into the context vector, providing *direct* geometric information about the *previously-decided* tooth surface. For v0, this is the *direct* analog of "current crown part conditioned on the previously-generated tooth part + the prep-tooth + adjacent + opposing" — replace "previous parts" with "previously-decided dental parts" and the *exact* same autoregressive context mechanism applies. The *qualitative* ablation (Fig 8a: parts overlap/intersect without the autoregressive context) is the *evidence* that the *fused* previous-parts code is *essential* for *part-coherence* — the *direct* support for the *H3* analog "current tooth part is *coherent* with the *previously-generated* tooth part".

**H4 (implicit SDF > explicit mesh) — STRONG PARTIAL CONTRADICTION, same as HoloPart.** AutoPartGen's *output* is an *explicit* mesh (via marching cubes from the VAE latent), the *direct* contradiction to H4's "implicit > explicit". But the *internal* representation is the VAE's *implicit* 3D latent (the (M, D) shape latent, decoded by a neural network to occupancy logits, NOT a mesh), the *hybrid* stance consistent with H4 for the *representation* and the *explicit* stance for the *output*. The CD 0.012 on whole-object reconstruction is the *evidence* that the *hybrid* approach is *robust*.

**H5 (synthetic pretrain + light fine-tune generalizes to real) — STRONG INDIRECT SUPPORT, *via* the *large-scale* training data.** AutoPartGen is *trained* on ~300K Objaverse-XL assets (~2M parts) — a *massive* scale-up vs PartGen (10× more data) and HoloPart (2× more data). The 300K-asset / 2M-part scale is the *direct* evidence that *large-scale* Objaverse pretraining *enables* the SOTA performance on PartObjaverse-Tiny. For v0, this is the *strong* support for the v0 corpus-curation strategy (per paper 094's recommendation): *first* curate a *large* 3D asset corpus, *then* fine-tune on the *small* dental domain, the *practical* H5 mechanism for v0 v0.

## Surprises

1. **The *killer* discovery: 3DShape2VecSet latent is *inherently compositional*.** The empirical property 𝒛 = 𝒛⁽¹⁾ ⊕ 𝒛⁽²⁾ decodes to 𝒙 = 𝒙⁽¹⁾ ∪ 𝒙⁽²⁾ is the *single most important* finding in 2025 3D-gen — it *unlocks* autoregressive part-3D-generation *without* requiring the decoder to learn part-blending (the *traditional* challenge in NeRF/SDF/Gaussian Splatting composition). For v0, the *direct* implication: if v0 uses 3DShape2VecSet as the latent (per HoloPart 094 + TripoSG + CLAY stack), the *compositional* property is *automatically* inherited — no additional engineering needed for *multi-crown composition* (e.g., v0 v2's full-arch generation).

2. **AutoPartGen *beats* HoloPart *without* using 3D masks.** This is the *surprising* result: HoloPart has *more* input information (partial 3D + 3D part masks) than AutoPartGen (partial 3D + 2D masks only), yet AutoPartGen *still* wins on every metric (CD 0.047 vs 0.065 on parts, 0.012 vs 0.018 on whole). The *explanation*: the *autoregressive* structure of AutoPartGen *implicitly* learns to *predict* the part *structure* from the 2D masks + partial 3D, *without* requiring the *explicit* 3D part mask that HoloPart needs. For v0, the *direct* implication: v0 can use AutoPartGen *without* needing a *separate* 3D part segmentation model (the *engineering* simplification vs HoloPart).

3. **The `[EoT]` empty-shape stop token is the *killer* mechanism for variable-part-count.** The *learned* stop signal (the model emits a special `[EoT]` token representing an *empty* part → stop generation) is the *only* mechanism in the literature that *automatically discovers* the *number* and *type* of parts. For v0 v2's *variable* 6-part dental scheme (per paper 091/092 recommendations: occlusal + 2 axial + margin + 2 proximal-contact = 6 parts for *most* teeth, but incisors may have *fewer* parts, molars may have *more* parts), AutoPartGen's `[EoT]` mechanism is the *natural* fit. For v0 v0, the *practical* mechanism: train AutoPartGen on a *diverse* set of dental crowns, let the *learned* `[EoT]` decide how many parts each crown needs.

4. **The *single* 24-layer DiT handles *all three* scenarios.** The same model is trained for (1) object-to-parts decomposition, (2) image-to-parts generation, (3) masks-to-parts reconstruction, with *only* the conditioning dropout mechanism. This is the *first* 3D-part-generation paper to *unify* all three tasks into a *single* model, vs PartGen's *three separate* multi-view diffusion models and HoloPart's *two-stage* (SAMPart3D + HoloPart) pipeline. For v0, the *direct* implication: a *single* v0 v0 model handles *all* v0 sub-task 4 scenarios (crown from prep scan + crown from photo + crown from annotated masks), the *engineering* simplification.

5. **The *fusion* mechanism E(∪ⱼ sample_N D(·|𝒛⁽ʲ⁾)) is the *engineering* trick for context.** The previous-parts conditioning 𝒛⁽¹⁾∪⋯∪𝒛⁽ᵏ⁻¹⁾ is computed by *re-encoding* the previously generated parts through the VAE encoder E (the *expensive* but *correct* way to get a *single* context vector for all previous parts). For v0, the *direct* template: use the *same* E re-encoding trick for the *previously-decided* dental parts (e.g., after generating the occlusal part, re-encode it + the margin + 2 axial → get the *fused* code for the *next* proximal part).

6. **The 256 H100 × 4 days training cost is *prohibitive* for v0 v0 (~$30,000+ Lambda).** The full model training requires *massive* compute. For v0 v0, the *practical* path: *fine-tune* the *pre-trained* AutoPartGen weights (released on GitHub) on the *dental* domain, the *engineering* shortcut. The fine-tuning cost on a *dental* corpus of 30-50K meshes is *only* 4×RTX 4090 × 2 days = 64 GPU-hours = **$200-400 Lambda**, the *practical* v0 v0 budget. For v0 v1, the fine-tuning cost is *only* 8×A100 × 1 day = 64 GPU-hours, the *production* budget.

7. **The autoregressive inference is *slower* than HoloPart's parallel inference.** The autoregressive loop generates one part at a time, requiring *K* sequential forward passes (vs HoloPart's *one* forward pass per part). For a 6-part dental crown, AutoPartGen takes ~6× the *sequential* inference time of HoloPart. The *mitigation*: parallelize the *denoising* within each part (the 20-50 steps per part are *already* parallelizable). For v0 v1, the *target* inference time is <5s per crown — AutoPartGen on a 6-part crown takes ~10-30s on 1×A100, *not* <5s. The *practical* mitigation: (i) use the *masks-to-parts* scenario with *parallel* part generation when masks are available, (ii) fine-tune the *step count* via consistency-model distillation (the *future* direction, not yet published for AutoPartGen).

8. **The `w_img=7, w_geom=4` defaults are *similar* to HoloPart's `S=3.5`.** The two CFG scales for AutoPartGen (w_img and w_geom) are *separate* knobs (modulating image vs geometry conditioning strength), vs HoloPart's *single* guidance scale. For v0, the *practical* mechanism: ablate the two CFG scales *separately* on the v0 dental dataset — w_img=7 likely needs *reduction* for *high-quality* dental crowns (the image conditioning may *overpower* the geometry prior, leading to *blurry* occlusal details), w_geom=4 likely needs *increase* for *fine* dental detail (the geometry prior should be *stronger* than the image).

9. **The dataset pipeline inherits from PartGen but *scales* 10×.** The 300K-asset / 2M-part scale is *substantially* larger than PartGen's ~30K-asset / ~300K-part scale, the *direct* evidence that the *scaling* hypothesis (more data → better quality) *holds* for 3D-part-generation. For v0, the *direct* template: scale the v0 dental corpus to *at least* 30-50K meshes (per the existing 3DTeethSeg22 + ToothFairy2/3 + DCrownFormer + Hosseinimanesh + ToothForge datasets), the *minimal* scale for AutoPartGen-style fine-tuning.

10. **The applications section is *vague*.** The paper's applications (3D scene + city generation) are *high-level* but lack *quantitative* evaluation. The *implication* for v0: the *killer* v0 application of AutoPartGen is *not* 3D scene or city generation, but rather *interactive dental part-level editing* (v0 v2) where the autoregressive structure enables *predictable* part-level modifications (modify part k, re-generate parts k+1, K to maintain coherence).
