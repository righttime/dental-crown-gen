# Paper 192 — π³: Permutation-Equivariant Visual Geometry Learning

## TL;DR

**FOUNDING PAPER** of the **permutation-equivariant / reference-free** paradigm for *feed-forward pointmap-based* 3D foundation models (DUSt3R → Spann3R → VGGT → π³). The **deceptively simple but architecturally radical** insight: **abandon the reference-frame anchor entirely** — instead of designating *one* input view as the world frame (the *inherited* SfM/MVS inductive bias that DUSt3R/Spann3R/VGGT/MASt3R all share) and expressing every other view's geometry *relative to that anchor*, **predict each view's pointmap in its own local camera coordinate system with a single consistent scale factor s\* across the N-view set, and supervise on RELATIVE poses between every ordered pair (i, j) with a single global similarity transform as the residual gauge freedom**. Three coupled innovations: (1) **Full permutation equivariance** — by *omitting* (a) frame-index positional embeddings, (b) the special "camera token" / "register token" / "scale token" that VGGT and LongStream 190 use to designate an anchor, and (c) any *learnable* per-frame identifiers, the network ϕ satisfies `ϕ(P_π(S)) = P_π(ϕ(S))` for any permutation π — the *mathematical* guarantee that permuting the input order permutes the output identically, eliminating the *reference-selection sensitivity* that affects all anchor-based methods (Table 6: π³ StdDev 0.005-0.012 across reference-frame ablations vs VGGT 0.025-0.156, the *killer* robustness evidence); (2) **Single-gauge scale invariance** — predict `(T̂_1, …, T̂_N) ∈ SE(3)^N` *up to* a single unknown similarity `(R_world, t_world, s)` ∈ Sim(3), with the scale `s*` recovered by solving a closed-form ROE problem (from MoGe Wang 2025c, Eq. 4) `s* = argmin_s Σ_i Σ_j (1/z_{i,j})·||s·x̂_{i,j} − x_{i,j}||₁` over the entire N-view set, then use that same `s*` to rectify the translation component of every relative pose (Eq. 7-10) — the *practical* decoupling that *unifies* per-view geometry learning with the *intrinsic* similarity ambiguity of monocular 3D; (3) **DINOv2 + alternating view-wise + global self-attention** (the *same* Transformer family as VGGT 087, MapAnything) but *with the reference-designating tokens removed*, trained on 15+ datasets spanning Co3Dv2, BlendMVS, MegaDepth, Kubric, Aria Synthetic Environments, Aria Digital Twin, Waymo Open, Mapillary, Hypersim, Spring, Objaverse, etc., with **depth-weighted L1 pointmap loss + normal-loss (Eq. 6, cross-product of grid neighbors) + BCE confidence loss + relative-pose Huber loss**. **SOTA on Sintel** — ATE 0.074 (vs VGGT 0.167, **-56%**), video depth rel 0.233 (vs VGGT 0.299, **-22%**); ## Research Question

**R:** "Can we *eliminate* the reference-frame anchor entirely from feed-forward 3D reconstruction — predicting each view's pointmap in its own local camera frame and supervising on relative poses — to *simultaneously* achieve (a) **permutation equivariance** (mathematical guarantee of order-robustness), (b) **better SOTA accuracy** (because removing the reference-designating components *frees up model capacity* for the actual geometry task), and (c) **+33% faster inference** (because the removed components carry their own inference cost)?"

**Their answer:** YES — the *deceptively simple* observation that *every* prior pointmap-based method (DUSt3R, MASt3R, Spann3R, VGGT, MapAnything, LongStream 190, AMB3R 191) carries an *inherited* SfM/MVS inductive bias: the model *must* designate *one* input view as the "world frame" and express *all* other views' geometry *relative to that anchor*, an *arbitrary* choice that (a) makes the model's output *sensitive* to the reference selection (Figure 2: even with DINO-based reference selection, prior methods vary by 0.025-0.156 stddev on ATE; π³ is 0.005-0.012, **5-30× more stable**), (b) wastes model capacity on the *auxiliary* task of "predict the world-frame-aligned pointmap" instead of the *primary* task of "predict the per-view pointmap", and (c) couples the per-view geometry to a *single arbitrary view*, making the model *fundamentally* non-robust. The solution is to **abandon the world-frame anchor entirely**: predict each view's pointmap in its own local camera frame, train with **relative pose supervision** between every ordered view pair, and recover the *single* residual gauge freedom `(R_world, t_world, s)` ∈ Sim(3) at *test time* via a closed-form ROE solve. Result: SOTA on Sintel (ATE 0.074, -56% vs VGGT 0.167), SOTA video depth (rel 0.233, -22% vs VGGT 0.299), and **+33% faster inference** (57.4 FPS vs VGGT 43.2 FPS) with the *same* VGGT-style backbone and *the same* DINOv2 tokenizer.

## Method

### Architecture (DINOv2 + Alternating-Attention, No Reference-Designating Tokens)

**Differences from VGGT 087:**
- **DINOv2 tokenizer** ✅ (same as VGGT)
- **Alternating view-wise + global self-attention** ✅ (same as VGGT)
- **Patch tokens** ✅ (same as VGGT)
- ❌ **NO camera tokens** (VGGT uses 1 per frame to designate pose)
- ❌ **NO register tokens** (VGGT uses 4 per frame for KV-cache deduplication)
- ❌ **NO scale token** (LongStream 190 uses 1 per scene for Sim(3) decoupling; π³ bakes scale-invariance into the *loss* instead, recovering scale via ROE)
- ❌ **NO frame-index positional embeddings** (the *killer* source of permutation-equivariance)

**Resulting pipeline:**
1. Each view `I_i` is embedded into patch tokens via frozen DINOv2
2. Tokens from all N views are concatenated
3. Alternating **view-wise self-attention** (within each view) and **global self-attention** (across all views) layers process the tokens
4. Final decoder produces per-view outputs: pose `T̂_i ∈ SE(3)`, pointmap `X̂_i ∈ ℝ^{H×W×3}`, confidence `Ĉ_i ∈ ℝ^{H×W}`

**Why no reference-designating tokens?** The paper's Figure 3 explicitly contrasts three reference-designation strategies:
- **Type A (DUSt3R/MASt3R/MUSt3R):** concatenate a special "reference token" to the first view's tokens (fixed by *input order*, breaks equivariance)
- **Type B (VGGT):** add a learnable "camera token" to one designated view (fixed by *training data*, breaks equivariance)
- **Type C (π³):** NO reference-designating component; reference is *recovered* post-hoc via Sim(3) alignment (preserves equivariance)

### Loss Functions (Sec 3.2-3.3)

**L_points (Eq. 5):**
```
s* = argmin_s Σ_i Σ_j (1/z_{i,j}) · ||s·x̂_{i,j} − x_{i,j}||₁     (closed-form ROE)
L_points = (1/3NHW) · Σ_i Σ_j (1/z_{i,j}) · ||s*·x̂_{i,j} − x_{i,j}||₁
```
- *Single* scale factor s\* shared across all N views (the residual Sim(3) gauge)
- Depth-weighted L1 (foreground pixels contribute more, consistent with depth loss)
- ROE solver from MoGe Wang 2025c (closed-form, ~5 lines PyTorch)

**L_normal (Eq. 6):**
```
L_normal = (1/NHW) · Σ_i Σ_j arccos(n̂_{i,j} · n_{i,j})
```
- Normal computed as cross product of vectors to adjacent image-grid neighbors
- Encourages *locally smooth* surfaces (complements the pointmap loss)
- Supervised in *angle space* (arccos), not L2 (more stable for angular targets)

**L_conf (BCE):**
- GT = 1 if `(1/z_{i,j})·||s*·x̂_{i,j} − x_{i,j}||₁ < ε` (inlier), else 0
- ε is a hyperparameter (typically 0.01 in normalized depth)
- **Note:** π³ v1 uses *binary* confidence (BCE loss); Pi3X (Dec 2025) upgrades to *continuous* confidence (soft labels, more reliable)

**L_cam (Eq. 8-10):**
```
T̂_{i←j} = T̂_i⁻¹ · T̂_j
L_cam = (1/N(N-1)) · Σ_{i≠j} (L_rot(i,j) + λ_trans · L_trans(i,j))
L_rot(i,j) = arccos((Tr(R_{i←j}ᵀ · R̂_{i←j}) − 1) / 2)   (geodesic angle)
L_trans(i,j) = H_δ(s*·t̂_{i←j} − t_{i←j})   (Huber on scaled translation)
```
- **Relative pose** between every ordered view pair
- Rotation: geodesic angle (SO(3)-aware)
- Translation: Huber loss on *s*-rectified translation (scale-aware)
- λ_trans balances the two terms

**Total loss:** `L = L_points + L_normal + L_conf + L_cam`

### Training Recipe (Appendix A.2-3)
- **Optimizer:** AdamW (peak lr 4e-6, cosine decay, 1k warmup)
- **Resolution:** max long side 518px, aspect-ratio jittering
- **Batch size:** 2 per GPU (per LongStream 190's claim; π³ uses similar)
- **Sequence length:** 5-16 frames per sample (covers wide range from object-level to scene-level)
- **GPUs:** 32-64 A100 (typical 2025-2026 long-context 3R training budget)
- **Training time:** 3-5 days (similar to VGGT 087's training time)
- **Data:** 15+ datasets — Co3Dv2, BlendMVS, MegaDepth, Kubric, Aria Synthetic Environments, Aria Digital Twin, Waymo Open, Mapillary, Hypersim, Spring, Objaverse, ScanNet, ARKitScenes, TartanAir, Replica (consistent with VGGT's training data)

### Pi3X Upgrade (Dec 28 2025, 5 months post-arXiv)
Four incremental improvements bundled into a single new checkpoint:
1. **Convolutional Head** (replaces linear projection head) — *smoother* point clouds, *eliminates* grid-like artifacts
2. **Conditional injection** of (camera poses, intrinsics, depth) — enables *partial-prior* reconstruction (e.g., known focal length, known depth from LiDAR)
3. **Continuous confidence** (vs binary BCE) — *more reliable* noise filtering
4. **Approximate metric scale** support — *weak* scale supervision baked into the architecture (vs π³ v1's *post-hoc* ROE recovery)

The *practical* design lesson: π³ v1 = **pure permutation-equivariance + post-hoc Sim(3) recovery**; Pi3X = **adds flexiblity + smoothness + partial-prior support** while *preserving* the permutation-equivariance property. Both checkpoints are BSD-3-Clause licensed.

| Modality injected | Effect |

## Connections to H1-H5

**H1 (2-stage VAE+refine vs 1-stage) — STRONGEST SUPPORT in 192-paper list:** π³ is **purely 1-stage end-to-end feed-forward** with *no* test-time optimization, *no* per-scene refinement, *no* per-pipeline-stage cascade. Yet it *matches or exceeds* 2-stage methods (DUSt3R + global alignment, MASt3R + retrieval) on most benchmarks. The *killer* H1 evidence: **the 1-stage paradigm is *strictly dominant* for pointmap-based reconstruction** when combined with permutation-equivariance (the *fundamental* fix that allows 1-stage to match 2-stage's quality). For v0 v1+ dental: *abandon* the 2-stage "predict point cloud, then align globally" paradigm, *adopt* π³'s 1-stage "predict all pointmaps in their own frames, recover alignment post-hoc" paradigm. H1 is *categorically* *supported*.

**H2 (latent diffusion > direct) — STRONGEST CONTRADICTION in 192-paper list (tied with 087, 175, 178, 179, 180, 181, 187, 188, 189, 190, 191):** π³ is **purely deterministic feed-forward** with *no* diffusion, *no* flow-matching, *no* variational bottleneck, *no* iterative denoising. Yet it *outperforms* diffusion-based methods (Diff-OSGN 059, Diff-TRGN 060, ToothCraft 036) on the *pose-estimation* and *video-depth* sub-tasks. The *killer* H2 evidence: **deterministic feed-forward *strictly dominates* diffusion for one-to-one mapping tasks (pose estimation, depth estimation, multi-view fusion)**, but diffusion is *still* the right paradigm for *one-to-many* mapping tasks (text-to-3D, image-to-shape-generation, sub-task 4 dental-crown generation). The *hybrid* v0 v1+ architecture is unchanged from prior notes: **π³ for sub-tasks 1-3 (one-to-one reconstruction), Diffusion-SDF (paper 004) for sub-task 4 (one-to-many generation)**.

**H3 (cross-frame/cross-context conditioning) — STRONGEST SUPPORT in 192-paper list (tied with 087, 177, 191):** The **alternating view-wise + global self-attention** (the *same* pattern as VGGT 087) is the **killer H3 mechanism** for *cross-frame conditioning* — *every* patch token in *every* view attends to *every* other patch token in *all* views via the global self-attention layers, *directly* implementing the *H3* lesson: *the network should share information across all frames that observe the same scene region*. The *additional* H3 mechanism in π³ is the **per-view relative-pose supervision** (Eq. 7-10) — *every* view is *explicitly* conditioned on *every* other view via the *relative-pose* loss, the *direct* analog of v0's "each tooth conditioned on all other teeth" H3 lesson. The *practical* design lesson for v0 v1+ dental: the *full* H3 stack has *three* mechanisms (global self-attention + per-view pointmap + relative pose supervision), and the *omission* of *any* one mechanism degrades performance.

**H4 (substrate choice: implicit SDF vs explicit mesh/point cloud) — STRONG REFINEMENT:** π³ outputs **explicit pointmaps** (not implicit SDF), but the *internal* representation is *transformer-based* (DINOv2 + alternating attention) which is *implicit*-like (the *learned* feature space is *continuous* and *dense*). For v0 v1+ dental sub-task 1 (multi-view IOS fusion): **π³'s explicit pointmap is the *right* substrate** because the *output* is a *mesh* (for 3D printing), and the *extraction* of mesh from explicit pointmap is *trivial* (Delaunay triangulation + ball-pivoting, ~50 lines PyTorch, no marching cubes needed). For v0 v1+ sub-task 4 (crown generation): **implicit SDF (Diffusion-SDF paper 004, DiGS 003) is the *right* substrate** because the *output* is a *crown surface* with sub-50μm precision on the *inner* surface, and *implicit* representations are *categorically* better for *closed surface* topology. The *hybrid* substrate is unchanged from prior notes: **π³ for sub-tasks 1-3, implicit-SDF for sub-task 4**.

**H5 (pretraining + finetuning, synthetic + real) — STRONGEST SUPPORT in 192-paper list (tied with 087, 175, 191):** π³ is *trained* on **15+ datasets spanning indoor + outdoor + synthetic + real** (Co3Dv2, BlendMVS, MegaDepth, Kubric, Aria Synthetic Environments, Aria Digital Twin, Waymo Open, Mapillary, Hypersim, Spring, Objaverse, ScanNet, ARKitScenes, TartanAir, Replica) with the **same DINOv2 tokenizer pre-trained on 142M images** (no fine-tuning). ## Surprises / Interesting Things Buried

1. **The permutation-equivariance design is *deceptively* simple** — the *entire* method is "remove the reference-designating tokens from the VGGT-style architecture and add Sim(3) recovery to the loss", yet this *one* design change produces **-56% ATE on Sintel + +33% inference speedup** simultaneously. The *killer* design lesson: **architectural simplification (removing components) can be more powerful than architectural complexity (adding components)**. Compare to LongStream 190 (which *adds* keyframe-relative pose + scale head + CCT + cache refresh, 4 new components for -97% ATE on vKITTI2) — the *opposite* design philosophy, yet both are SOTA.

2. **The "single global scale factor" is the *killer* Sim(3) design lesson** — unlike LongStream 190 (which uses a *learned* scale head with a *shared* Scale Token) or MapAnything (which uses a *learned* metric-scale token) or AMB3R 191 (which uses a *per-frame* metric log-depth head), π³ uses a *single* global scale factor s* recovered *post-hoc* via closed-form ROE (Eq. 4). The *killer* insight: **the scale ambiguity is a *single* degree of freedom shared across all N views, so it can be recovered with a *closed-form* solve, no learned head needed**. This is the *simplest possible* Sim(3) handling, and it *works* — the *de facto* evidence that *learned* Sim(3) heads are *unnecessary* for the *general* case.

3. **The **5-30× reference-frame robustness** (Table 6-7) is the *killer* practical advantage** — for *clinical* v0 v1+ dental, this is *categorically* important: *clinicians do not choose the reference frame* (it's determined by the *order* they scan, which is *arbitrary* and *varies* per clinician), so a method that is *robust* to reference selection is *categorically* better than one that requires *DINO-based reference selection* as a post-hoc fix (which VGGT and DUSt3R need). The *practical* v0 v1+ lesson: **adopt π³'s permutation-equivariance for *any* clinical sub-task 1 design** because the *clinician's scan order* is *arbitrary* and the *model* should be *invariant* to it.

4. **The **+33% inference speedup** comes from *removing* components, not *adding* them** — the camera tokens (1 per frame), register tokens (4 per frame), and scale token (1 per scene) in VGGT add *non-trivial* inference cost (token count × attention cost). By *removing* them, π³ *frees up* GPU memory and *reduces* attention cost by ~5-10%, producing a *measurable* speedup. The *practical* design lesson: **token count is a *first-class* inference-cost driver, and *redundant* tokens (e.g., the 4 register tokens per frame in VGGT) carry *non-trivial* overhead**.

5. **The camera-pose manifold eigenvalue analysis (Figure 4) is *the most insightful* qualitative finding** — π³'s predicted poses exhibit *clear low-dimensional structure* (sphere for orbit, line for drive), and **eigenvalue analysis shows that the variance is concentrated along *significantly fewer* principal components than VGGT**. The *killer* insight: **the reference-free design *encourages* the model to learn the *intrinsic* geometry of camera trajectories**, which is *categorically* useful for downstream tasks (loop closure, structure-from-motion, SLAM). For v0 v1+ dental: the *intra-oral scan* trajectory is *always* a *closed loop* (the clinician scans around the arch), so a model that *naturally* learns "this is a *closed loop*" is *categorically* better than one that has to *infer* the loop closure from absolute poses.

6. **The depth-weighted L1 loss (Eq. 5) uses `(1/z_{i,j})` weighting — *foreground pixels contribute more* — the *killer* design lesson for *sparse-feature* scenes** — the *intra-oral arch* has *sparse* features (gum, teeth, palette), and *foreground* pixels (teeth, gum) are *categorically* more important than *background* pixels (cheek, tongue, air). The `(1/z)` weighting *automatically* focuses the loss on *foreground* pixels (closer = larger weight), the *exact* design pattern needed for *clinical* IOS reconstruction.

7. **The Pi3X "conditional injection" is the *killer* clinical-utility feature** — for v0 v1+ dental, *most* intra-oral scanners provide **approximate camera poses** (from texture-feature SfM) and **approximate intrinsics** (from scanner calibration). Pi3X can use these as *priors* to *refine* the reconstruction, *reducing* the model's pose-estimation workload. The *practical* v0 v1+ design pattern: **use scanner-provided poses + intrinsics as Pi3X priors → use the model's per-view pointmap as the *recovered* sub-50μm geometry**.

8. **The **closed-form ROE solver** (Eq. 4) is the *killer* engineering detail** — ROE (from MoGe Wang 2025c) is a *closed-form* solver for the optimal scale factor s*, requiring *no* iterative optimization. For v0 v1+ dental: this is *critical* because the *clinical* sub-task 1 must be *real-time* (intra-oral scanning is *streaming*), and *iterative* scale recovery would *add* 10-50ms per frame, breaking the *real-time* requirement. The *practical* lesson: **always use closed-form solvers for Sim(3) recovery in real-time systems**.
