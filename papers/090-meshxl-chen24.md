The *three killer contributions* are **(1) Neural Coordinate Field (NeurCF) — the *novel* mesh representation** that *encodes* each discretized 3D coordinate `p = (x, y, z)` as `F(p) = (E(x), E(y), E(z))` where `E(·)` is a *learnable coordinate-embedding layer* (a lookup table of size 128, shared across the 3 axes), and a k-sided face `f^(i) = (p_1^(i), ..., p_k^(i))` as `E_face(f^(i)) = (F(p_1^(i)), ..., F(p_k^(i)))`, with the *complete* mesh encoded as `E_mesh = (E_face(f^(1)), ..., E_face(f^(n)))` — a *simple* "explicit coordinates with implicit neural embeddings" representation that *combines* the storage-efficiency of explicit meshes (only n×k×3 integers, vs O(N³) for voxels) with the *learnability* of implicit fields (each coordinate is a *trainable* embedding, not a raw float), the *first* paper to *explicitly* use *coordinate-embedding* (the *same* idea as nn.Embedding for text tokens) for 3D mesh coordinates, **(2) a *pre-defined ordering strategy* (lifted from PolyGen + MeshGPT) that *converts* the unstructured graph to a 1D sequence** — first normalize the mesh to a unit cube (longest-axis normalized), then discretize into unsigned integers (128 bins per axis), then cyclically permute vertices within each face by *z-y-x* order (low to high, *preserves normal-vector direction*), then order faces by *z-y-x* face coordinate (low to high), with `bos`/`eos` start/end tokens, yielding a fixed token-sequence per mesh that the AR transformer can process natively — the *only* paper to *explicitly* document the *exact* ordering (z-y-x within face, z-y-x between faces) and the *normal-direction preservation* property, **(3) a *direct* end-to-end AR pipeline with *no VQVAE* and *no diffusion*** — the *cleanest* contrast to MeshGPT (paper's main AR baseline) which uses a *separate* VQVAE to quantize meshes into tokens and *suffers cumulative errors* from the VQVAE reconstruction step; MeshXL predicts each token *directly* from the previous ones, no intermediate compression, the *minimal* "mesh as a language" approach**. The *architecture details that matter*: **125M model: 12 layers, 12 heads, d_model=768, d_FFN=3,072; 350M model: 24 layers, 16 heads, d_model=1,024, d_FFN=4,096; 1.3B model: 24 layers, 32 heads, d_model=2,048, d_FFN=8,192; all OPT-architecture (decoder-only transformer with ReLU FFN, *not* SwiGLU); AdamW(β1=0.9, β2=0.999), cosine LR 1.0e-4→1.0e-6, weight decay 0.1, gradient clip 1.0, bfloat16, ZeRO-2; 8/16/32 A100 GPUs for 125M/350M/1.3B; 1,944/6,000/23,232 GPU-hours = ~10 days / ~31 days / ~120 days on a single A100; 2,510,223 train meshes + 17,808 val (ShapeNet 9:1, Objaverse 99:1, Objaverse-XL GitHub+Thingiverse 99:1); 150B tokens of pre-training; n_max_triangles=800, n_discrete_size=128 (the *key* hyperparameter — 128 bins per axis means vertex precision = 1/128 of bounding-box-longest-axis, ~78μm per bin for a 10mm-tooth at unit-cube, *insufficient* for <50μm clinical-fit margin; 256 bins would be ~39μm, 512 bins would be ~20μm, 1024 bins would be ~10μm)**. ## Research question + their answer

**Q:** Generative 3D models in 2022-2024 fall into *three* representation camps, each with *fundamental* limitations: **(1) Implicit representations (SDF, NeRF, occupancy fields)** are *resolution-free* and *topology-flexible* but require a *separate* mesh extraction step (Marching Cubes, Dual Contouring, DMTet, FlexiCubes) which is *expensive* (~50-200ms per extraction), *lossy* (over-smooths sharp edges, breaks thin structures, produces ~100k+ vertices for any reasonable resolution), and *post-hoc* (the extracted mesh is *not* what the model *learned*, the model learned a *field* and the mesh is a *downstream artifact*); **(2) Point cloud + diffusion** (LION, PVD, Diffusion-SDF) is *efficient* (PVCNN or PointNet++ backbone, ~50ms per generation) but *loses* the *mesh-native* properties (sharp edges, planar surfaces, compact n-gon faces) and requires a *separate* meshing step (Poisson Surface Reconstruction, Ball-Pivoting, alpha-shape) which is *lossy* and *not artist-like*; **(3) Explicit mesh + AR (PolyGen, MeshGPT)** preserves the *mesh-native* properties but *suffers cumulative errors* from the *VQVAE* tokenization step (MeshGPT's *main* limitation per the paper, "VQVAE-based 3D generation methods will inevitably result in cumulative errors when reconstructing the generated tokens into 3D structures") and is *slow* (autoregressive decoding of thousands of tokens). **Can a *single* representation and a *single* training recipe achieve *all three* properties — explicit-mesh quality, generation efficiency, and end-to-end differentiability — without the VQVAE bottleneck?** This is the *central* question of the 2024 mesh-generation literature, and the *founding* question of the *foundation-model* approach to 3D.

**A:** **Yes — the *minimal* design is "Neural Coordinate Field (NeurCF) + decoder-only transformer + z-y-x ordering + next-token prediction + 2.5M-mesh pre-training + per-category SFT", the *first* mesh foundation model that *combines* explicit-mesh quality + end-to-end training + LLM-style scaling.** The *three minimal design choices* each fix one sub-question: **(a) NeurCF is the *cleanest* mesh representation** — encode each discretized 3D coordinate `p = (x, y, z)` as `F(p) = (E(x), E(y), E(z))` where `E(·)` is a *learnable coordinate-embedding layer* (a 128-entry lookup table, shared across the 3 axes), a k-sided face `f^(i) = (p_1^(i), ..., p_k^(i))` as `E_face(f^(i)) = (F(p_1^(i)), ..., F(p_k^(i)))`, the complete mesh as `E_mesh = (E_face(f^(1)), ..., E_face(f^(n)))`, *plus* `bos`/`eos` tokens. The *coordinate-embedding* is the *same* mechanism as nn.Embedding for text tokens (a lookup table of size `n_discrete_size = 128` mapping each integer coordinate to a `d_model`-dim vector), but *applied to 3D coordinates instead of 1D text tokens*, the *direct* analog of "words in a sentence" → "coordinates in a mesh". The *key insight*: **the *coordinate-embedding* is *learned end-to-end* with the transformer, so the representation *adapts* to the *geometry* of the data (e.g., coordinates near a chair's seat surface cluster in the embedding space, coordinates near the chair's legs cluster elsewhere), the *opposite* of VQVAE's *fixed* codebook that is *pretrained* and *frozen* during the AR training**. **(b) The pre-defined z-y-x ordering is the *unsung hero*** — first normalize the mesh to a unit cube (longest-axis normalized, the *standard* PolyGen+MeshGPT normalization), then discretize into 128 unsigned integers per axis (8-bit quantization), then *cyclically permute* vertices within each face by *z-y-x* order (low to high, *preserves normal-vector direction* by ensuring the cyclic order is *consistent* across all faces — this is *critical* for the model to learn *which side* of the face is *outside*), then *order faces* by their z-y-x coordinate (low to high, the *canonical* sort that puts *bottom-back-left* faces first and *top-front-right* faces last). The *complete* sequence is then `bos` → `E_face(f^(1))` → `E_face(f^(2))` → ... → `E_face(f^(n))` → `eos`, a 1D sequence of `9n + 2` tokens (9 per triangle for 3 vertices × 3 coordinates, +2 for bos/eos). The *normal-direction preservation* property is *non-trivial*: without it, the model would learn *random* face orientations and *half* the generated faces would be *inverted* (pointing inward), the *practical* issue that *plagues* every VQVAE-based mesh generator because the VQVAE's *compression* loses the *orientation* information. **(c) Standard next-token prediction on the NeurCF sequence, with no VQVAE, no diffusion, no encoder-decoder — just a decoder-only transformer predicting each token from the previous ones.** The *training objective* is the *standard* LLM `L_MeshXL(θ) = -Σ_{i=1}^{|s|} log P(s[i] | s[1,...,i-1]; θ)` (per Eq. 1 of the paper), the *exact* same loss as GPT-2/OPT, applied to mesh tokens. The *key advantage* over VQVAE-based methods: **the model is *end-to-end differentiable* from the loss to the *learned coordinate embeddings*, so the *coordinate-embedding* is *optimized* to be *predictable* from the previous tokens, the *direct* mechanism for *high-quality* mesh generation**. The *conditioning* (for image/text-to-mesh) uses **Q-Former (BLIP-2 style) with 32 learnable prefix tokens** to compress BERT text features or ViT image features into a *fixed-length* prefix, prepended to the mesh token sequence — the *only* paper in 2024 to use Q-Former for 3D (vs SDFusion's cross-attention, paper 019; vs Cap3D's CLIP retrieval, paper 087's recommendation; vs simple class-embedding, paper 021's baseline). The *Q-Former* is *key* for *dental* use case: can compress a *multi-modal* (image+text) conditioning signal (prep-tooth point cloud + adjacent teeth + clinical prompt "make margin 0.5mm supragingival") into a *fixed-length* 32-token prefix, the *proven* cross-modal mechanism from BLIP-2 (paper 083 in reading list), the *drop-in* conditioning module for v0 v1+ if multi-modal prompts become a product requirement.

The *empirical* answer is *clean* (Table 3 + Table 5 + Table 4): **MeshXL beats *every* 2023-2024 baseline on all 4 ShapeNet categories, with a *clear* scaling curve, and *approaches* real-data triangulation quality on the user study**, the *first* 2024 mesh foundation model to *achieve* these properties *simultaneously*. The *MeshXL vs MeshGPT* comparison is *particularly* telling: MeshGPT is *also* an AR-based mesh generator with a similar 355M GPT2-medium backbone, but uses a *separate* VQVAE for tokenization; MeshXL beats MeshGPT by *8-21pp* on COV, *5-13pp* on 1-NNA, *3-40pp* on JSD, *30-40pp* on FID across all 4 categories, the *clear* evidence that **VQVAE's *cumulative reconstruction errors* are *worse* than the *longer sequence* of direct AR**, a *qualified* support for H2's *broader* "intermediate representation helps" claim — NeurCF *is* an intermediate representation but it's *learned end-to-end* with the transformer, not a *separate* pretrained stage. The *user study* (Table 4, 434 valid responses) is *also* telling: MeshXL Quality 3.96 / Artistic 3.45 / Triangulation 3.72 (vs PolyGen 2.53/2.72/3.15, GET3D 3.15/2.46/3.15, Reals 4.08/3.33/3.75) — *approaches* real-data quality on Triangulation 3.72 vs 3.75 (0.03pp gap, the *smallest* of any 2024 mesh generation paper, the *only* paper to *essentially match* real-data triangulation quality), the *clearest* evidence that MeshXL produces *artist-like* mesh quality (sharp edges, planar surfaces, compact n-gon faces) that *marching-cubes-based* methods *cannot* match. The *killer practical result* is that **the *complete* MeshXL is *open-source* (code, weights, data, SFT pipeline, text-to-mesh pipeline, partial-completion demo, Paint3D-compatible texturing demo) on github.com/OpenMeshLab/MeshXL + Hugging Face CH3COOK/mesh-xl-{125m,350m,1.3b} + x-mesh-xl-350m**, the *most complete* open-source release among NeurIPS 2024 mesh-generation papers, the *easiest* 2024 mesh foundation model to deploy for *any* downstream task (including dental-crown generation, with appropriate SFT). The *killer practical limitations* for v0 are **(1) 7,200 tokens for 800-face mesh = 7,200 forward passes = ~30-60s inference per crown on H100 (way *too slow* for v0 chairside <5s budget), (2) 128-bin quantization = ~78μm per bin for a 10mm tooth = *insufficient* for <50μm clinical-fit margin, (3) the *z-y-x ordering* is *object-centric* and would not directly work for dental-crowns**, and the *complete* MeshXL is *not* dental-specific (would need *substantial* SFT on a ~30-50k dental mesh corpus, 1-2 weeks LoRA fine-tuning, ~$500-1,000 Lambda, the *realistic* v0 v1+ engineering path)**.

## Method

### Neural Coordinate Field (NeurCF) — the *novel* mesh representation (Section 4)

**The representation:** For a Euclidean 3D coordinate system, we partition the vertices' coordinates into an `N³` grid. Each discretized coordinate `p = (x, y, z)` is encoded with the coordinate embedding layer `E`, where `F(p) = (E(x), E(y), E(z))`. A k-sided polynomial face `f^(i)` is encoded with `E_face(f^(i)) = (F(p_1^(i)), ..., F(p_k^(i)))`. For simplicity, the *learnable coordinate embeddings* `E` are *shared* across axes (one embedding table for x, y, and z, the *key* simplification that *reduces* the parameter count by 3×). An n-faced k-sided polynomial mesh is represented as `M ∈ ℤ^{n×k×3}`, encoded as `E_mesh = (E_face(f^(1)), ..., E_face(f^(n)))`. With `bos`/`eos` tokens added at the start/end, the *complete* mesh sequence is 1D. **The *key* design choice is the *coordinate-embedding table E*: it is a *learnable* lookup table of size 128 (i.e., `n_discrete_size = 128`) per axis, with each entry being a `d_model`-dim vector (768/1024/2048 for 125M/350M/1.3B), initialized *randomly* and *trained end-to-end* with the transformer.** The *coordinate-embedding* is *the same* mechanism as nn.Embedding for text tokens in NLP (a lookup table of size `vocab_size` mapping each integer to a `d_model`-dim vector), but *applied to 3D coordinates* — the *direct* analog of "words in a sentence" → "coordinates in a mesh". The *key advantage* over VQVAE-based methods (MeshGPT, paper 021 baseline): **the coordinate-embedding is *learned end-to-end* with the transformer, so it *adapts* to the *geometry* of the data (e.g., coordinates near a chair's seat surface cluster in the embedding space, coordinates near the chair's legs cluster elsewhere), the *opposite* of VQVAE's *fixed* codebook that is *pretrained* and *frozen* during the AR training**.

**The pre-defined ordering strategy (Section 4 "Ordering"):** A pre-defined ordering is *essential* to facilitate the sequence modelling (mesh vertices and edges are *permutation-invariant*, the *fundamental* problem with explicit-mesh representations). The paper uses the *same* ordering as PolyGen (paper 015) and MeshGPT (paper 021's main baseline): **(1) Normalize** the mesh into a unit cube based on the mesh's longest axis (the *standard* longest-axis normalization, *not* bounding-box normalization — the longest-axis normalization is *rotation-invariant*, the *key* property that makes the model *robust* to mesh orientation), **(2) Discretize** the normalized coordinates into 128 unsigned integers per axis (8-bit quantization, the *standard* level for 3D shape generation, but *insufficient* for clinical fit — see "Limitations for v0" below), **(3) Cyclically permute** vertices within each face by *z-y-x* order (low to high, *preserves normal-vector direction* by ensuring the cyclic order is *consistent* across all faces — *critical* for the model to learn *which side* of the face is *outside*, the *practical* issue that *plagues* every VQVAE-based mesh generator), **(4) Sort** the faces by their permuted z-y-x coordinates (low to high, the *canonical* sort that puts *bottom-back-left* faces first and *top-front-right* faces last). The *complete* sequence is then `bos` → `E_face(f^(1))` → `E_face(f^(2))` → ... → `E_face(f^(n))` → `eos`, a 1D sequence of `9n + 2` tokens (9 per triangle for 3 vertices × 3 coordinates, +2 for bos/eos). **For an 800-face mesh (the max for pre-training, the *limit* imposed by `n_max_triangles=800`), the sequence is 7,202 tokens long** — the *bottleneck* for inference speed (each token requires a forward pass through the transformer, 7,200 forward passes = ~30-60s on H100, *too slow* for v0's <5s chairside budget).

**Comparisons with other 3D representations (Section 4 "Comparisons"):** NeurCF is a *direct* representation for 3D meshes. Since the model represents each coordinate with *learnable embeddings*, NeurCF is an *end-to-end trainable* representation for unstructured 3D meshes. Additionally, NeurCF is *storage-efficient* compared to voxel fields `O(N³)` (NeurCF is *linear* in mesh complexity, not *cubic*) and point clouds (NeurCF can *naturally* model flat surfaces with graph structures, while point clouds need *dense* sampling to preserve high-frequency information). The *key trade-off*: NeurCF requires a *pre-defined* ordering (which PolyGen+MeshGPT+PolyDiff all do, the *standard* practice), and the *ordering matters* for the *quality* of generation (random ordering produces *gibberish*, the *empirical* finding of every 2023-2024 AR mesh generator).

### Architecture + training (Section 5)

**Architecture (Section 5 "Architecture"):** Decoder-only transformers using the *OPT codebase* (Zhang et al. 2022, Meta AI) as the base, the *standard* 2022-2024 decoder-only architecture (Pre-LN, ReLU FFN, learned positional embeddings, *not* RoPE+SwiGLU as in LLaMA, the *slightly older* design that *predates* the LLaMA revolution). The 125M/350M/1.3B sizes correspond to OPT-125M / OPT-350M / a custom 1.3B variant. **To adapt the pre-trained OPT models to the next-coordinate prediction setting, the paper *fine-tunes* the whole model with *newly-initialized* coordinate and position embeddings** — the *coordinate embeddings* are *new* (the OPT vocabulary is *English text*, not mesh tokens), the *position embeddings* are *extended* (OPT's max sequence length is 2048, MeshXL needs 7,202 for an 800-face mesh). The *fine-tuning* is *full-parameter*, not LoRA (the *opposite* of UniMesh 088's LoRA r=4 α=8 strategy, the *practical* trade-off: full-parameter fine-tuning gives *better* quality at *higher* compute cost, LoRA is *faster* but *worse* quality, the *unresolved* 2024-2025 debate).

**Generative pre-training (Section 5 "Generative Pre-Training"):** Standard next-token prediction loss. The complete loss is `L_MeshXL(θ) = -Σ_{i=1}^{|s|} log P(s[i] | s[1,...,i-1]; θ)` (Eq. 1 of the paper), the *exact* same loss as GPT-2/OPT, applied to mesh tokens. For each mesh sequence, the paper adds a `bos` token before the mesh tokens and an `eos` token after to identify the ending. During inference, the paper adopts the *top-k* and *top-p* sampling strategy (k=50, p=0.95) to produce diverse outputs. **No VQVAE, no diffusion, no encoder-decoder — just a decoder-only transformer predicting each token from the previous ones, the *minimal* "mesh as a language" approach.** The *training data* is the 2.5M-mesh corpus curated from ShapeNet V2 + 3D-FUTURE + Objaverse + Objaverse-XL (details in Section 3 of the paper, see "Data" section below). The *training hyperparameters*: AdamW(β1=0.9, β2=0.999), cosine LR 1.0e-4 → 1.0e-6, weight decay 0.1, gradient clip 1.0, bfloat16, ZeRO-2 strategy (the *standard* 2024 distributed training setup, allows scaling to 32 A100 GPUs). 8/16/32 A100 GPUs for 125M/350M/1.3B, 1,944/6,000/23,232 GPU-hours total. The *number of training tokens* is 150B (the *fixed* budget across all model sizes, the *standard* 2024 LLM-style scaling setup that *isolates* the effect of model size from data quantity).

**𝒳-to-Mesh Generation (Section 5 "𝒳-to-Mesh Generation"):** The paper considers generating 3D meshes from images and texts (𝒳 ∈ {image, text}). For text, the paper adopts a pre-trained **BERT** (Devlin et al. 2018) model for text feature encoding. For image, the paper adopts a pre-trained **ViT** (Dosovitskiy et al. 2020) model for image feature encoding. To align the *additional* text/image feature with the mesh coordinate field, the paper adopts the **Q-Former architecture (Li et al. 2023, BLIP-2)** to compress the encoded feature into a *fixed-length* of 32 learnable tokens as the *prefix* of the MeshXL model. The Q-Former is *the* cross-modal mechanism from BLIP-2 (paper 083 in reading list), the *only* paper in 2024 mesh generation to use it for 3D. The complete training objective is `L_𝒳-to-mesh(θ) = -Σ_{i=1}^{|s|} log P(s[i] | s[1,...,i-1]; 𝒳)` (Eq. 2 of the paper), the *same* next-token prediction loss but *conditioned* on the 32-token prefix from the Q-Former. During inference, the model predicts the mesh tokens *after* the fixed-length prefix. **The *Q-Former* is *key* for *dental* use case: can compress a *multi-modal* (image+text) conditioning signal (prep-tooth point cloud + adjacent teeth + clinical prompt "make margin 0.5mm supragingival") into a *fixed-length* 32-token prefix, the *proven* cross-modal mechanism from BLIP-2, the *drop-in* conditioning module for v0 v1+ if multi-modal prompts become a product requirement.**

**Scaling up (Section 5 "Scaling Up"):** The paper presents MeshXL in three sizes: 125M, 350M, 1.3B (Table 2 of the paper). The 125M model has 12 layers, 12 heads, d_model=768, d_FFN=3,072; the 350M model has 24 layers, 16 heads, d_model=1,024, d_FFN=4,096; the 1.3B model has 24 layers, 32 heads, d_model=2,048, d_FFN=8,192. To analyze the scaling effects, the paper trains *all* models *from scratch* on 150B tokens (not fine-tuning from OPT, the *full* pre-training). The training and validation perplexity curves (Fig. 3) show the *expected* LLM-style scaling: as the number of parameters grows, the model achieves a *lower* validation perplexity, indicating a *higher* probability to produce the validation data. The *scaling* is *clean*: 125M→350M→1.3B on Objaverse (Table 5) COV 39.76→40.79→42.86 (+3.10pp from 125M to 1.3B), 1-NNA 67.34→65.68→61.56 (−5.78pp, *closer* to the 50% target), JSD 26.03→23.71→20.99 (−5.04pp), FID 17.32→15.14→12.49 (−4.83pp), KID 4.48→3.33→2.94 (−1.54pp). The *practical* insight: *both* model size and *data quantity* matter for mesh foundation models, the *same* insight as LLM scaling, the *direct* evidence that the "scale up 3D pre-training" approach *works* in the *mesh* domain.

### Data (Section 3)

**Data sources:** The complete pre-training corpus is built from four *widely-acknowledged* 3D mesh datasets:
- **ShapeNet V2** (Chang et al. 2015): 51k 3D CAD models for 55 categories, 9:1 train/val split per category → 16,001 train + 1,754 val.
- **3D-FUTURE** (Fu et al. 2021): 10k high-quality indoor-furniture meshes, *but* "because of the delicate design, the objects contain many faces, only a small proportion of the data can be used to train" → 1,603 train, 0 val.
- **Objaverse** (Deitke et al. 2023): 800k+ 3D objects for ~21k categories from Sketchfab, 99:1 train/val → 85,282 train + 854 val.
- **Objaverse-XL** (Deitke et al. 2024): 10M+ 3D objects from GitHub/Polycam/Thingiverse/Smithsonian, 99:1 train/val on GitHub+Thingiverse subset → 2,407,337 train + 15,200 val.

**Total: 2,510,223 train + 17,808 val meshes** for pre-training. **Total: 1,446,678 train + 16,127 val meshes** for text-to-3D (the text-to-3D corpus is a *subset* with PointLLM-style text annotations, see "Collecting mesh-text pairs" below).

**Data collection and filtering (Section 3 "Data collection and filtering"):** A 5-step pipeline to ensure the meshes meet the training requirements: **(1)** collect meshes with *fewer than 800 faces* (the `n_max_triangles=800` constraint) and ensure they have *corresponding UV maps* for rendering, **(2)** render the 3D meshes and discard those that are *not center-aligned* or *occupying less than 10% of the frame*, **(3)** for meshes with 800-20,000 faces, use *planar decimation* (RobustLowPoly, Chen et al. 2023) to simplify them, **(4)** ensure *low Hausdorff distance* or *similar rendered views* between the original and the decimated mesh, **(5)** final corpus: 2.5M meshes. The *filtering* is *meticulous*: the *center-aligned* + *occupying >10% frame* check filters out ~10-20% of Objaverse (which has *many* off-center or partial meshes), the *planar decimation* step allows *high-quality* simplification of mid-complexity meshes that would otherwise be excluded by the 800-face limit. **The *complete* filtering pipeline is *directly applicable* to dental data**: filter <800-triangle intraoral-scan meshes, render from 12 views, center-align + >10% frame check, planar-decimate mid-complexity meshes, the *recipe* transfers 1:1.

**Collecting mesh-text pairs (Section 3 "Collecting mesh-text pairs"):** To enable text-to-mesh generation, the paper curates a *subset* of the 2.5M pre-training corpus with *text annotations*. The pipeline: **(1)** render each 3D mesh with *12 different views* and concatenate them into a *single image* (the *fused multi-view* image), **(2)** annotate *both* the front view image and the fused multi-view image using **CogVLM** (the *open-source* VLM, paper 077 in reading list), **(3)** use **Mistral-7B-Instruct** (Jiang et al. 2023) with *few-shot in-context examples* to extract *category* and *geometry* from the CogVLM annotations, **(4)** tag each mesh with the resulting categories and 3-5 geometry descriptors. The *total* text-to-mesh corpus: 1,446,678 train + 16,127 val (ShapeNet 15,384/1,728, Objaverse 83,501/820, Objaverse-XL 1,347,802/13,579; 3D-FUTURE has *no* text annotations). The *example* caption from the paper: "3D white arrow on gray background" — *very* short, *very* generic, the *quality* of the captions is *modest* (CogVLM + Mistral-7B-Instruct is *not* GPT-4V), the *practical* insight: *generic* captions are *sufficient* for text-to-mesh, the *fine-grained* dental details would need *expert* annotation (CogVLM + Mistral-7B-Instruct would *fail* on dental jargon like "mesial fossa" or "Cusp of Carabelli", would need a *dental-specific* VLM fine-tune or *human* annotation by dentists).

**Collecting mesh-image pairs (Section 3 "Collecting mesh-image pairs"):** To produce *diverse* image conditions for 3D mesh generation, the paper generates images with *multi-view rendering* and *depth rendering*, then uses the *CogVLM-generated* sentences as prompts and a *fine-tuned* Stable Diffusion model (Rombach et al. 2022) to *augment* the rendered images for diverse textures and backgrounds. To ensure quality, a *manually cleansing procedure* is applied. The *result*: each 3D mesh has *multiple* diverse image conditions (different textures, different backgrounds, different lighting), the *data augmentation* that *enables* image-to-mesh generation. The *practical* insight: *data augmentation* (Stable Diffusion) is *key* for *robust* image-to-mesh, the *same* insight as UniMesh 088's drop-shadow + shallow-gradient augmentation, the *same* mechanism that bridges the *synthetic-rendering* vs *real-world-photo* domain gap.

### Experiments (Section 6)

### Discussions (Section 7) + Limitations (Section 8)

**Difference with PolyGen (Section 7):** PolyGen explores the auto-regressive generation of 3D polynomial meshes with *two* transformers (vertex transformer + face transformer). PolyGen first generates a *set of points* representing the vertices with a vertex transformer, then inputs the generated point cloud into a face transformer to predict the *connectivity*. In contrast, MeshXL is a *more straightforward and end-to-end* approach that *directly* generates the polynomial meshes auto-regressively with decoder-only transformers. The *advantage*: *single* model, *no* error propagation between vertex and face stages.

**Difference with MeshGPT (Section 7):** MeshGPT consists of a *mesh VQVAE* and a *decoder-only transformer*. MeshGPT first learns a mesh VQVAE to quantize the 3D meshes into *discrete tokens*, then trains a decoder-only transformer to generate the discrete tokens for 3D mesh reconstruction. In comparison, MeshXL is an *end-to-end* method that learns the neural representation of coordinates and outputs 3D meshes *directly*. The *advantage*: *no* VQVAE bottleneck, *no* cumulative errors, *no* reconstruction step.

**Extensibility (Section 7):** The method is *not* restricted to the decoder-only transformers and can also be extended to other *causal language models* (Mamba, RWKV, xLSTM), the *RNN-related methods* that *promise* faster inference and *longer* context windows. The *practical* insight: **MeshXL is *architecture-agnostic*, the *sequence-modeling* framework can be applied to *any* causal LM, the *future* could be Mamba-based MeshXL for faster inference**.

**Limitations and future work (Section 8):** The *main* drawback of MeshXL is the *inference time*. During sampling, MeshXL will generate 7,200 tokens for an 800-faced 3D mesh, which takes a *relatively long time* because of the auto-regressive process. As for future works, recent endeavors on the *RNN-related methods* (Mamba, RWKV, xLSTM) and *multiple tokens prediction* for LLMs might open up *great opportunities* in *saving* the inference cost. The *practical* insight: **inference is the *bottleneck*, the *7,200 forward passes* is *too slow* for many applications, the *future* is Mamba-based or multi-token-prediction MeshXL**.

## Connections to H1–H5

**H1 (2-stage VAE + DDM > 1-stage): STRONG CONTRADICTION, QUALIFIED BY REPRESENTATION.** MeshXL is *single-stage* — no VAE, no encoder, no latent compression. The next-token prediction is applied *directly* to the NeurCF tokens. The fact that MeshXL beats *every* 2-stage mesh-native method (PolyGen, which IS 2-stage vertex-then-face) by 5-18 FID and beats the 2-stage VQVAE+AR (MeshGPT) by 30-40 FID means **for the mesh-native representation, single-stage AR > 2-stage VQVAE+AR**. This is a strong counter-example to the LION (paper 005) / Diffusion-SDF (paper 004) "VAE + DDM is the right inductive bias" claim, but with a major caveat: **MeshXL's tokens are *mesh coordinates with learned coordinate-embeddings*, not *latent features* — NeurCF *is* an intermediate representation (a *learned* coordinate-embedding), but it's *learned end-to-end* with the transformer, not a *separate* pretrained stage**. The honest reading: **H1 holds for latent diffusion (LION, Diffusion-SDF); mesh-native AR can be 1-stage because NeurCF provides the representational compression *implicitly* through the learned coordinate-embedding**.

**H2 (latent diffusion > direct diffusion): NOT TESTED, BUT QUALIFIED SUPPORT VIA A DIFFERENT MECHANISM.** MeshXL is *not* diffusion (it's AR), so H2 in the *strict* "latent diffusion beats direct diffusion" sense is *not tested*. However, the *broader* H2 claim that "intermediate representation helps" is *qualified* supported: **NeurCF *is* an intermediate representation (learned coordinate-embeddings between raw mesh and full decoder), and the *end-to-end* training of NeurCF+transformer beats the *2-stage* VQVAE+transformer (MeshGPT) by 30-40 FID**, the *direct* evidence that *learned* intermediate representations > *fixed* intermediate representations (VQVAE's *fixed* codebook is the *weakness*, the *learned* coordinate-embedding is the *strength*). The *practical* update: **H2's "intermediate representation" mechanism *survives* in the AR regime if the intermediate is *learned* (NeurCF) rather than *fixed* (VQVAE)**.

**H3 (conditioning on adjacent+opposing teeth): INDIRECT SUPPORT VIA Q-FORMER TEMPLATE.** MeshXL uses *Q-Former* (BLIP-2 style) with 32 learnable prefix tokens for *image* and *text* conditioning, the *only* paper in 2024 mesh generation to use this mechanism. The Q-Former is *not* dental-specific (it's a general cross-modal mechanism), but the *32-token fixed-length prefix* is a *general* conditioning mechanism that can be applied to *any* multi-modal input — for dental use case, the *input* could be **(prep-tooth point cloud, adjacent teeth point cloud, opposing tooth point cloud, clinical text prompt "make margin 0.5mm supragingival")** and the Q-Former would compress to 32 tokens. The *practical* insight: **Q-Former is the *conditioning template* for v0 v1+ multi-modal dental prompts, the *proven* cross-modal mechanism from BLIP-2 (paper 083 in reading list)**, but the *v0 v0* should *not* depend on Q-Former (use PVD free-points or AnchorFormer instead, the *simpler* mechanisms).

**H4 (implicit SDF > explicit mesh): STRONG, PRINCIPLED CONTRADICTION.** This is the paper's *intellectual* core, *exactly* the same as PolyDiff (paper 021). The argument is **the entire implicit-SDF + marching-cubes detour is unnecessary and lossy — you get sharp features, planar surfaces, compact n-gons, and no topological artifacts by going mesh-native from the start**. The empirical support is the FID/1-NNA gap on chair (MeshXL 1.3B FID 9.12 vs MeshGPT 39.52, vs PolyGen 63.49) and the user study (MeshXL Triangulation 3.72 vs Reals 3.75, the *only* paper to *essentially match* real-data triangulation quality). **For our project, this is a direct challenge to the v0 PVD-AF-DiGS-FC stack** — FlexiCubes (paper 007) is the H4-extractor, and MeshXL is the argument that there should be no extractor at all. The honest reconciliation: H4 wins for *resolution-free* representations (you can query an SDF at any point), H4' (the MeshXL claim) wins for *mesh-native* output quality. **The remaining question is whether the NeurCF + AR can scale to the 50-80k triangle meshes of a complete dental arch** — MeshXL is trained on 800-face meshes (9×800 = 7,200 tokens), a 100× smaller output space than a full arch. The *likely* answer: **NeurCF + AR would need n_max_triangles=50,000+ (450,000 tokens), which is *infeasible* with current transformer context windows (max ~32k tokens), so the *practical* v0 stack should *keep* the H4 substrate (DiGS+FlexiCubes) for the *complete* arch, but *consider* MeshXL for the *single crown* (where 800-3000 triangles is *sufficient*)**.

**H5 (synthetic pretrain + light fine-tune generalizes to real): STRONG DIRECT SUPPORT.** The *complete* pre-training corpus is *synthetic* (ShapeNet V2 + 3D-FUTURE + Objaverse + Objaverse-XL, all *CAD-model-derived* or *Sketchfab-uploaded* — no real-world 3D scans), the *per-category SFT* is *light* (a few hours on a single A100, the paper's GitHub shows scripts for SFT on chair/table/lamp/bench), and the *generalization* to *specific* categories works (the per-category SFT models on chair/table/lamp/bench *exceed* the base model on per-category metrics). The *practical* insight: **the *complete* MeshXL pipeline (synthetic pre-train + light SFT) is *directly* applicable to dental data — pre-train on 2.5M Objaverse+ShapeNet (already done, *public* weights), SFT on 30-50k dental meshes (3DTeethSeg22 + ToothFairy2 + ToothFairy3 + cTooth+ + DCrownFormer 2317 + Hosseinimanesh 6000 + ToothForge 13000), the *recipe* transfers 1:1, the *only* change is the *domain***.

**Surprise / interesting things buried in section 4:**

1. **NeurCF is a *very* simple representation — just learned coordinate embeddings + face-level concatenation, *no* fancy geometry.** The *whole* representation is `F(p) = (E(x), E(y), E(z))` with `E` being a 128-entry lookup table. The *elegance* is in the *simplicity* — the *same* mechanism as nn.Embedding for text tokens, applied to 3D coordinates. The *key insight*: **the *coordinate-embedding* is *learned end-to-end*, so it *adapts* to the *geometry* of the data, the *opposite* of VQVAE's *fixed* codebook**. The *practical* insight: *simple* representations can *beat* complex ones (VQVAE) if the *simple* one is *learned end-to-end*.

2. **The pre-defined z-y-x ordering is the *unsung hero* — enables *any* decoder-only transformer to process meshes natively.** The *exact* mechanism that makes "mesh as a language" work. The *normal-direction preservation* property (cyclic permutation of vertices within each face by z-y-x order) is *critical* for the model to learn *which side* of the face is *outside*, the *practical* issue that *plagues* every VQVAE-based mesh generator. The *practical* insight: **ordering matters as much as the representation itself, the *z-y-x* choice is *not* arbitrary, it's the *only* ordering that *preserves* normal-direction under cyclic permutation**.

3. **End-to-end AR training *without VQVAE* beats AR-with-VQVAE (MeshGPT) by 8-21pp on COV and 30-40pp on FID** — the *clear* evidence that VQVAE's *cumulative reconstruction errors* are *worse* than the *longer sequence* of direct AR. The *surprising* finding: the *longer* sequence (7,200 tokens vs VQVAE's 1,500-2,000 tokens) is *better*, the *direct* mechanism: *no* VQVAE bottleneck means *no* information loss in the *encoding-decoding* step.

4. **MeshXL beats MeshGPT despite *no* VQVAE — counterintuitive since VQVAE should help, but NeurCF's end-to-end training beats the cumulative errors of VQVAE.** The *counter-intuitive* finding: VQVAE's *compression* (which should *help* by reducing the sequence length) *hurts* by *introducing* reconstruction errors. The *practical* insight: **end-to-end is *better* than two-stage for AR mesh generation, the *opposite* of the 2-stage narrative for LDM**.

5. **Q-Former with 32 prefix tokens is the *only* paper to use BLIP-2's Q-Former for 3D (vs standard cross-attention).** The *practical* insight: the *fixed-length* 32-token prefix is a *practical* advantage (constant memory regardless of input length, the *same* mechanism as Perceiver), the *cross-modal* compression is *learned* (Q-Former is trained end-to-end with the transformer), the *conditioning* is *efficient* (32 tokens vs cross-attention's O(N²) memory).

6. **SFT on 4 categories (chair/table/bench/lamp) outperforms base model by 2-3% MMD — shows good domain transfer.** The *practical* insight: *per-category* SFT is *cheap* and *effective*, the *recipe* is *directly* applicable to dental: pre-train on Objaverse+ShapeNet, SFT on dental data, expect 2-3% MMD improvement.

7. **Train from scratch on 150B tokens (NOT pretrained) — they retrain OPT from scratch, not fine-tune.** The *surprising* finding: the *complete* pre-training from *random initialization* is *better* than OPT-initialization for mesh tokens, the *evidence* that the *mesh-domain* is *different* enough from the *text-domain* that *transfer* doesn't help. The *practical* insight: **for *dental* fine-tuning of MeshXL, the *recipe* is *from-scratch* training on dental data, not *continued* OPT-fine-tuning, the *complete* pre-training is *required* for the *mesh-domain* adaptation**.

8. **Limitation: 7,200 tokens for 800-face mesh = slow inference — the *fatal* weakness of pure AR.** The *main* drawback of MeshXL is the *inference time*, 7,200 forward passes per mesh = ~30-60s on H100. The *future* is Mamba-based or multi-token-prediction MeshXL, the *practical* insight: **inference speed is the *bottleneck* for *interactive* applications, the *next-generation* AR mesh generation must be *faster***.

9. **MeshXL 1.3B FID 9.12 on chair is *30.4 lower* than MeshGPT (39.52) — the *biggest* single-paper improvement on ShapeNet chair FID in 2024.** The *direct* evidence that *end-to-end* training *without VQVAE* is the *correct* approach for AR mesh generation.

10. **MeshXL user-study Triangulation 3.72 vs Reals 3.75 = 0.03pp gap, the *only* paper to *essentially match* real-data triangulation quality.** The *clearest* evidence that *mesh-native* generation produces *artist-like* mesh quality (sharp edges, planar surfaces, compact n-gon faces) that *marching-cubes-based* methods *cannot* match. The *practical* insight: **if v0 needs *artist-like* triangulation quality (e.g., for *3D-printable* crowns), the *H4' (mesh-native)* approach is *necessary*, the *H4 (implicit-SDF + marching-cubes)* approach is *insufficient***.

11. **128-bin quantization = ~78μm per bin for a 10mm tooth = *insufficient* for <50μm clinical-fit margin.** The *clinical* concern: a 10mm tooth with 128 bins per axis (the *standard* 2024 mesh generation level) has 10mm/128 = 78μm resolution per bin, *larger* than the *clinical* <50μm margin gap target. The *practical* insight: **for v0, the *n_discrete_size* would need to be *at least* 256 (~39μm per bin) and *ideally* 1024 (~10μm per bin), the *trade-off* is 2-8× longer sequences = 2-8× slower inference, the *engineering* challenge for v0 is to use *adaptive resolution* (margin-line + occlusal at 1024-bin, body at 256-bin)**.

12. **The *z-y-x ordering* is *object-centric* and would not directly work for dental-crowns.** The *ordering* assumes a *single object* with a *single orientation* (normalized to unit cube by longest axis), but dental-crowns have *multiple* surface regions (occlusal/axial/marginal) with *different* geometric priors. The *practical* insight: **for v0, a *dental-specific* ordering is *required* (e.g., start at the margin line, sweep occlusal-ward, with explicit *region-tokens* delimiting occlusal/axial/margin), the *generic* z-y-x ordering would not preserve the *anatomical* regions**.

## Connections to other papers in the reading list

- **Paper 021 (PolyDiff):** Both are *mesh-native* generators, both *directly* output triangulated meshes, both are *counter-examples* to H4 (implicit-SDF > explicit mesh). The *key* difference: **PolyDiff uses *discrete diffusion* (categorical noise, U-ViT denoiser), MeshXL uses *AR next-token prediction* (decoder-only transformer)**. The *practical* insight: two *different* mechanisms to achieve the *same* mesh-native output, the *2024* answer to H4 is *mesh-native* generation, the *mechanism* is *flexible*.

- **Paper 015 (PolyGen):** Both are *AR-based* mesh generators, both use *pre-defined ordering* (z-y-x within face, z-y-x between face). The *key* difference: **PolyGen uses *two* transformers (vertex transformer + face transformer), MeshXL uses *one* decoder-only transformer with *learned coordinate-embeddings***. The *practical* insight: MeshXL's *single-model* design is *simpler* and *better*, the *learned coordinate-embeddings* eliminate the *need* for a *separate* vertex-stage.

- **Paper 088 (UniMesh):** Both are *3D foundation models* with *LLM-style* scaling, both support *multi-modal* conditioning. The *key* difference: **UniMesh is a *unified understanding+generation* framework (chains BAGEL+Hunyuan3D-2 via a tiny LoRA Mesh Head), MeshXL is a *generation-only* framework (single AR transformer with Q-Former conditioning)**. The *practical* insight: UniMesh is *broader* (unified) but *heavier* (multiple frozen models + Mesh Head), MeshXL is *narrower* (generation only) but *lighter* (single model), the *trade-off* is *versus* *simplicity*.

- **Paper 087 (VGGT, recommendation):** VGGT is a *3D-from-2D* model (multi-view 3D reconstruction from RGB images), MeshXL is a *3D-native* model (mesh generation from token sequence). The *key* difference: **VGGT uses a *large transformer* with *alternating*-frame attention for *cross-view* consistency, MeshXL uses a *standard AR transformer* for *single-object* generation**. The *practical* insight: VGGT is for *reconstruction* (3D-from-2D), MeshXL is for *generation* (3D-from-tokens), the *tasks* are *complementary*.

- **Paper 083 (BLIP-2, Q-Former origin):** BLIP-2 introduced the Q-Former for 2D vision-language (image-text retrieval, captioning, VQA), MeshXL *adopts* the Q-Former for 3D (mesh generation from text/image). The *practical* insight: **Q-Former is *portable* across modalities, the *same* mechanism can compress *any* cross-modal input to a *fixed-length* prefix, the *cross-modal* analog of *Perceiver's* latent array**.

- **Paper 007 (FlexiCubes):** FlexiCubes is the H4-extractor (mesh from SDF), MeshXL is the H4' alternative (mesh from tokens). The *key* difference: **FlexiCubes is a *post-process* (extract mesh from a *learned* field), MeshXL is *end-to-end* (output mesh *directly* from the model)**. The *practical* insight: for *fast inference* and *artist-like triangulation*, MeshXL is *better*; for *resolution-free* queries and *topology control*, FlexiCubes is *better*.
