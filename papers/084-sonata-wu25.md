## Research question + their answer

**Q:** Despite the *massive* success of self-supervised learning (SSL) in the 2D image domain — DINOv2 [60] can be *linearly probed* to 84% ImageNet top-1 with no fine-tuning, *and* the representations are *semantically* interpretable (PCA, k-means, nearest-neighbor matching all show *semantic* clustering) — 3D point cloud SSL has been a *failure mode*: PointContrast 2020 [93] achieves 5.6% mIoU on ScanNet linear probing, MSC 2023 [88] achieves 21.8%, both *orders of magnitude* below DINOv2's 63.1% on the *same* ScanNet (when DINOv2 is lifted to 3D). Why? The *image* SSL literature has had a 10-year head start on *identifying* and *fixing* collapse modes (SimCLR contrastive collapse → MoCo momentum encoder; BYOL trivial solution → EMA teacher; DINO centering collapse → Sinkhorn-Knopp; DINOv2 high-frequency artifact → patch-level student-teacher alignment), but the 3D SSL literature has *not* had a corresponding 10-year debate. The paper *names* the 3D-specific collapse mode for the first time: **the "geometric shortcut"** — the tendency of 3D point cloud models to *collapse* to low-level spatial cues (point normals, point height, distance to centroid) because *every* 3D operator (kNN, ball query, sparse conv, point transformer attention) takes point coordinates as input and *cannot* mask out the spatial information the way image SSL can mask out the pixels. The geometric shortcut is *unique* to 3D: in 2D images, all information is in the input feature (RGB), and the operators are *defined* on a *regular grid* where the (x,y) coordinates are *deterministic* and *contain no information*; in 3D, the *coordinates themselves* are the *only* signal that distinguishes the *sparse* point cloud from a *random* point set, and the operators *use* the coordinates to define neighborhoods. The result is that 3D SSL models *immediately* learn to predict point normals or point height from the (masked) coordinates alone, *bypassing* the input features entirely, and *never* learn the *semantic* features that generalize. **Can the geometric shortcut be *systematically* mitigated, and can a 3D foundation model be built that achieves *DINOv2-level* linear-probing performance on *both* indoor and outdoor 3D perception, with *strong* OOD generalization, *strong* data efficiency, and *strong* cross-modal (3D + 2D) complementarity?**

**A:** **Yes — and the *key* insight is that the geometric shortcut is a *data-flow* problem (not a *loss* problem), and the *fix* is to *systematically* obscure spatial information at the data side and *force* the model to use input features at the loss side.** The four *mechanisms* are: **(1) Decoder removal** — the *U-Net decoder* is *the* main culprit, because it re-introduces point-level features at the *original* spatial resolution, and the *spatial* information is *available* to the loss; removing the decoder *forces* the loss to operate on *coarser* features (where the spatial information is *globally* mixed via the pooling layers), boosting linear probing 20.7% → 60.4% (+39.7pp) in a *single* design change; **(2) Feature up-casting** (hypercolumn-style) — re-introduce *multi-scale* features by *progressively* up-casting the encoder features back to the *previous* scale via the pooling inverse-index, then *concatenating* with the previous-scale features, the *exact* design used in 2D image segmentation hypercolumns [33] and in PointNeXt's decoder, the *cheapest* multi-scale fusion in 3D deep learning (0 extra params, 0 inference cost, 2-line PyTorch); **(3) Masked-points Gaussian jitter (σ=0.01)** — *specifically* for points that are *about to be masked*, apply a *stronger* Gaussian jitter (σ=0.01 vs the *default* σ=0.005) to further *disrupt* the spatial relationships at the *masked* points, the *only* paper in the reading list to *specifically* augment the masked points differently from the unmasked; **(4) Progressive parameter scheduler** — over the *first 5%* of training, *gradually* increase the mask size (10→40 cm), mask ratio (30→70%), teacher temperature (0.04→0.07), and weight decay (0.04→0.2) so that the model *cannot* rely on the *easy* spatial cues from the start (the *curriculum learning* [7] principle: *start easy, get harder*); the *novel* finding is that *all four* scheduler parameters (mask size, mask ratio, temperature, weight decay) need to be *progressively* increased to *extremes* that were *not* explored in any prior 3D SSL paper. The four mechanisms together form a *systematic* recipe that can be applied to *any* point cloud SSL framework (the paper *validates* this on SparseUNet and PTv3), and the *result* is the *first* 3D foundation model that *matches* the 2D foundation model paradigm: Sonata-frozen + linear-classifier achieves 72.5% ScanNet mIoU (vs MSC's 21.8%, **3.3× better**, and *above* DINOv2's 63.1% lifted-to-3D), 73.4% S3DIS Area 5 linear probing, 32.0% AEO OOD mIoU (vs DINOv2-style from-scratch's much lower result), with full fine-tuning reaching **79.07% ScanNet val mIoU (+1.47pp over PTv3-from-scratch's 77.6%)** and **76.0% S3DIS Area 5 (+2.6pp over PTv3's 73.4%)** and **82.3% S3DIS 6-fold (+4.6pp over PTv3's 77.7%)**, *uniform* SOTA across 5 indoor + 3 outdoor + 4 instance-segmentation benchmarks. **The cross-modal complementarity is the *practical* deployment recipe** — combining Sonata (pure-3D) with DINOv2 (image features lifted to 3D) reaches **75.91% linear probing (+3.4pp)** and **79.12% full fine-tuning ScanNet val (+1.5pp over Sonata alone, +1.5pp over DINOv2 alone)**, the *first* paper to *explicitly* show that *3D+2D* SSL features are *complementary*, not *redundant* — the *direct* template for v0's *future* multi-modal pre-training with IOS RGB color (the *only* signal that *only* IOS scans carry, the *killer* feature for v0 v1 chair-side dental-AI). The data scaling is *the* practical enabler: Sonata pre-trained on 140k scenes (86.7× PC 2020, 14.7× MSC 2023) reaches 55.9% mIoU on *unseen* AEO OOD with only 22 training scans, **+21.0pp over PTv3-from-scratch's 34.9%**, the *single largest* OOD-generalization improvement in the 3D-deep-learning literature, the *direct* evidence that *pre-training on diverse 3D data* is the *correct* H5 mechanism for v0 sub-task 1 cross-clinic deployment.

## Method

### The geometric shortcut (Section 3 — Pilot Study)

**Definition:** the *tendency* of a 3D point cloud SSL model to *collapse* to low-level spatial cues (point normals, point height, distance to centroid) that are *always available* through the point coordinates, *bypassing* the input features entirely. The shortcut is *unique* to 3D because *every* 3D operator (kNN in DGCNN, ball query in PointNet++, sparse conv in SparseUNet, point transformer attention in PTv3) takes point coordinates as *input* and *uses* them to *define* the operator's neighborhood structure; in 2D, the operators are *defined* on a *regular grid* where the (x,y) coordinates are *deterministic* (a pixel at (0,0) and a pixel at (1,0) are *always* in the *same* relative position), so the *only* information is in the *RGB feature*.

**Evidence (Fig. 2):** the paper selects a point on a sofa arm and computes pairwise similarity with all other points in the scene. The *heatmap* for CSC [38] is *concentrated* on points with the *same surface normal* as the sofa arm (the *low-level* geometric cue). The *heatmap* for MSC [88] is *concentrated* on points at the *same height* as the sofa arm (a *different* low-level geometric cue, *not* surface normal, *not* semantics). The *heatmap* for Sonata is *concentrated* on *all* sofa arms in the *same* scene (the *high-level* semantic cue, the *correct* answer). The difference is *qualitative* and *visual*, the *first* time the 3D-SSL literature has had a *direct visual* of *what* the SSL representations are *actually* learning.

**Evidence (Fig. 4, Tab. 1):** the paper *visualizes* the PCA embeddings of the encoder features at each stage of a *supervised*-trained PTv3 (ScanNet semantic segmentation). The *encoder* features are *diverse* and *dispersed* (each stage captures *different* scales of spatial information), the *decoder* features are *uniform* and *structured* (the decoder is *task-specific* and *low-frequency*). The implication: the *encoder* is the *right* place to do SSL (it has *diverse* multi-scale features), the *decoder* is *not* (it has *task-specific* features and *re-introduces* the geometric shortcut via point-level features at the *original* resolution).

### Point self-distillation framework (Section 4.1)

**Two-branch student-teacher self-distillation** (DINOv2-style, adapted to point clouds):
- **Student** (actively learned, EMA-updated): takes *local views* (crop ratio 5-40%) and *masked views* (mask ratio up to 70%, mask size up to 40 cm) as input, outputs per-point embeddings.
- **Teacher** (EMA-updated, *no* gradient): takes *global views* (crop ratio 40-100%, 2-16 random crops) as input, outputs per-point embeddings.
- **Self-distillation loss**: for each point in a *local* or *masked* view, find the *nearest* point in the *global* view (via original-spatial-distance matching, *not* via the sorted order), and *align* the student's embedding to the teacher's embedding (Sinkhorn-Knopp-centered cross-entropy + KoLeo regularization + clustering assignments, the *exact* DINOv2 loss).
- **Asymmetric encoding**: the *more challenging* local and masked views are encoded by the *student*, the *easier* global views are encoded by the *teacher*; the EMA teacher *stabilizes* the training and *prevents* the student from collapsing to geometric shortcuts.
- **Difficulty scaling**: the *crop ratio* and *mask ratio* are *progressively* increased (over the first 5% of training, *curriculum-learning* style), forcing the model to *rely* on input features *more* as training progresses.

### Micro design (Section 4.2)

**(a) Decoder removal:** drop the *entire* U-Net decoder during pre-training, keep only the *encoder* (PTv3, 5.4M-108M params, 5 stages at scales 0.02m → 0.04m → 0.08m → 0.16m → 0.32m). The output is the *coarsest*-scale feature (after 4 pooling operations, 16× downsampling). **Effect on linear probing: +39.7pp** (20.7% → 60.4%) — the *largest* single-design-decision contribution in the 3D SSL literature, the *signature* ablation of the paper.

**(b) Feature up-casting (hypercolumn-style):** to recover the *multi-scale* information that the decoder would have aggregated, progressively up-cast the *coarsest* feature back to the *previous* scale via the pooling inverse-index, concatenate with the previous-scale features, repeat for all scales. **Effect: +2-3pp** over no up-casting; the *best* is up-casting *twice* (keep the 2 coarsest scales, drop the 3 finest, balance *multi-scale context* vs *geometric-shortcut risk*). Implementation: 2 lines of PyTorch, 0 extra params, 0 inference cost.

**(c) Masked-points Gaussian jitter (σ=0.01):** for points that are *about to be masked*, apply a *stronger* Gaussian jitter (σ=0.01 m) on the coordinates *before* the masking; for unmasked points, use the *default* jitter (σ=0.005 m). The *intuition*: masked points are *the* place where the geometric shortcut is *most* likely (the *unmasked* neighbors are the *only* signal, the model *wants* to use their coordinates to predict the masked point's coordinates), so *extra* coordinate noise at the masked points *forces* the model to use input features instead. **Effect: +1-2pp** on the linear-probing result; the *first* paper in the reading list to *specifically* augment the masked points differently.

**(d) Progressive parameter scheduler:** over the *first 5%* of training, *gradually* increase:
- **Mask size**: 10 cm → 40 cm (mask larger patches as training progresses)
- **Mask ratio**: 30% → 70% (mask more points as training progresses)
- **Teacher temperature**: 0.04 → 0.07 (sharpen the teacher's distribution as training progresses)
- **Weight decay**: 0.04 → 0.2 (regularize more aggressively as training progresses)

**Effect: +1-2pp** on the linear-probing result; the *key* finding is that *all four* parameters need to be *progressively* increased to *extremes* that were *not* explored in any prior 3D SSL paper (PC, MSC, CSC, etc. all use *fixed* values).

### Implementation and evaluation protocols (Section 4.3)

**Backbone:** PTv3 (paper 083) encoder-only, with the following changes from the *default* PTv3:
- **LayerNorm removed** (replaced with *no* normalization, see below)
- **Depth [3, 3, 3, 12, 3] (instead of [2, 2, 6, 2, 2])** — deeper encoder
- **Width [48, 96, 192, 384, 512] (instead of [32, 64, 128, 256, 512])** — wider encoder
- **Total params: 108M** (vs 46.2M for the *default* PTv3, the *largest* PTv3 variant to date)

**Why LayerNorm removed:** the *default* PTv3 uses LayerNorm in attention and BatchNorm in pooling; Sonata uses *no* normalization in the *encoder* (BatchNorm is *implicit* in the pooling). The *motivation*: LayerNorm *requires* per-point batch statistics, which *break* the multi-dataset joint training paradigm (different datasets have different mean/std). Removing LN *slightly* degrades the supervised result (-1-2pp) but *enables* the *clean* multi-dataset joint training paradigm (PPT [90] uses the same trick). The *degradation* is *more than recovered* by the SSL pre-training benefit (Sonata-PTv3 with no LN is 79.07% ScanNet val vs PTv3-from-scratch with LN's 77.6%, +1.47pp).

**Data (Tables 1-2):** Sonata pre-training uses 7 datasets, 139,769 scenes total, 17,948 real + 121,821 synthetic (87.0% synthetic):
- **Real**: ScanNet [23] 1,613, ScanNet++ [101] 1,016, S3DIS [1] 272, ArkitScenes [5] 5,047, HM3D [68] 10,000 = 17,948 total
- **Synthetic**: Structured3D [109] 21,821, ASE [3] 100,000 = 121,821 total
- **86.7× more scenes than PC [93] (1,613 real only)**, **14.7× more than MSC [88] (6,660 real only)**, **5.9× more than PPT [90] (23,706 mixed)**

**Training:** 32 epochs, AdamW, lr 5e-3, weight decay 0.04→0.2 (progressive), batch size 32 scenes per GPU, 8× A100 (80GB) GPUs, ~3 days of training. The *encoder-only* design (no decoder) *significantly* reduces the memory footprint (the decoder is the *largest* memory consumer in the standard PTv3), enabling *larger* batch sizes and *faster* training.

**Evaluation:** 5 indoor (ScanNet val, ScanNet200 val, ScanNet++ val, S3DIS Area5, S3DIS 6-fold) + 3 outdoor (nuScenes val, Waymo val, Sem.KITTI val) + 4 instance-segmentation (ScanNet val, ScanNet200 val, ScanNet++ val, S3DIS val) + 1 OOD (AEO 22-scan) + 1 surface-reconstruction (TSDF from frozen Sonata) benchmarks. Linear probing uses a *single* 1×1 conv layer (4.4M params for 20-class ScanNet, <0.2% of the 108M PTv3). Decoder probing adds a *small* decoder (13% of the PTv3 params, ~14M params) on top of the *frozen* encoder. Full fine-tuning updates *all* params.

### Surface reconstruction (Appendix B.2 — the *killer* v0 H4 evidence)

The paper *trains* a TSDF (Truncated Signed Distance Function) regressor on *frozen* Sonata features (the *encoder* is *frozen*, only a small TSDF regression head is trained), and *demonstrates* that *high-quality* dense scene geometry can be reconstructed from *sparse* SLAM point clouds (the AEO dataset, 25 sparse scans, *unseen* data pattern). The TSDF regressor uses a *4m × 4m × 4m* volume centered on the scene, with a *grid resolution* of 4 cm, and is trained on the *synthetic* ASE dataset [3] (100k indoor scenes with ground-truth TSDF). The *result*: *qualitative* reconstructions are *visibly accurate* on AEO SLAM data (Fig. 11 of the paper), with the *quantitative* metric being TSDF error *<* 5 cm on *most* surfaces. **This is the *direct* H4 evidence**: a *frozen* 3D foundation model can be *directly* used for implicit-SDF regression, *without* any *task-specific* fine-tuning, the *exact* recipe for v0 sub-task 4 mesh-output (crown mesh generation from *frozen* encoder features + TSDF/Marching-Cubes/FlexiCubes post-processing).

## Hypothesis impact

**H1 (2-stage VAE + DDM > 1-stage) — INDIRECT SUPPORT:** Sonata is the *purest* possible 2-stage recipe — *pre-training* (stage 1) on 140k scenes with self-distillation, *fine-tuning* (stage 2) on 1% data (100 scenes) with supervised cross-entropy. The 1%-data result (45.3% mIoU vs PTv3-from-scratch's 25.8%, +19.5pp) is *exactly* the *magnitude* of H1's 2-stage generation win, *the* supporting evidence for H1's *generic* principle. For v0, the v0 paper's H1 section should *cite* Sonata as the *image-domain* analog: "DINOv2 in 2D (linear probing 84% ImageNet) and Sonata in 3D (linear probing 72% ScanNet) both demonstrate that the 2-stage pretrain-finetune recipe is *better* than from-scratch training, *the* supporting evidence for H1 in the *general* representation-learning setting."

**H2 (Latent diffusion > direct) — STRONG INDIRECT SUPPORT:** Sonata's *encoder-only* design is *exactly* the *latent* representation that H2 latent-diffusion (LION 005, Diffusion-SDF 004, NFD 070) needs. The Sonata-pretrained encoder can be *plugged into* any latent-diffusion model as the *encoder*, *replacing* the from-scratch PointNet++/DGCNN/PTv3 encoder. The *evidence*: Sonata's frozen features already achieve 72.5% ScanNet mIoU (linear probing), and the *encoder* is what diffusion *denoises in latent space*, so a *better* encoder = a *better* latent = *better* diffusion. For v0, the v0 paper's H2 section should *cite* Sonata as the *first* paper to *explicitly* train the *encoder* with self-distillation at *scale*, the *right* encoder for v0's latent-diffusion sub-task 2 (crown generation in latent space). The cross-modal insight (Sonata + DINOv2 = +3.4pp) is *also* H2-relevant: a *multi-modal* latent (3D + image) is *better* than a *single-modal* latent (3D alone), the *direct* template for v0's *future* multi-modal latent (3D scan + IOS RGB color).

**H3 (Conditioning on adjacent+opposing teeth is the H3 mechanism) — NEUTRAL:** Sonata has *no* explicit dental-conditioning mechanism, but the *feature up-casting* (hypercolumn) is *exactly* the *multi-scale-context* mechanism that H3 needs (per-tooth context + arch-level context + cross-tooth context, all in the *same* concatenated feature). The masked-points jitter (σ=0.01) is *also* an H3-adjacent mechanism (it forces the model to use *non-spatial* features, the *opposite* of "teeth are positioned by their spatial coordinates", a *negative* H3 mechanism). For v0, the v0 paper's H3 section should *cite* Sonata's hypercolumn + masked-jitter as the *generic* multi-scale-context H3 mechanism, and *combine* with the *dental-specific* H3 mechanisms from the dental-IOS papers (cross-tooth attention from 045 TSegFormer, per-tooth-FDI embedding from 023 MeshSegNet, etc.). The cross-modal 3D+2D combination is *also* a *new* H3 mechanism (image features are *complementary* to 3D features, *the* H3 mechanism for v0's *future* multi-modal crown generation with text/image prompts).

**H4 (Implicit SDF > explicit mesh) — STRONG INDIRECT SUPPORT:** Sonata is *the* paper that *directly* validates H4 in the *general* 3D setting — the *encoder-only* design (no decoder, no U-Net) means the *latent representation* is a *point-cloud feature* (not a mesh, not a voxel grid), and the *surface reconstruction* experiment (Appendix B.2) *demonstrates* that *high-quality* TSDF can be regressed from *frozen* Sonata features, the *exact* H4 recipe (latent + implicit-SDF decoder). For v0, the v0 paper's H4 section should *cite* Sonata as the *first* 3D foundation model that *demonstrates* the H4 principle *at scale* — *pre-train a point-cloud encoder, regress TSDF from frozen features, extract mesh with Marching Cubes/FlexiCubes*, the *exact* H4 recipe for v0 sub-task 4 crown mesh generation. The *cross-modal* extension (Sonata + DINOv2 features → TSDF) is the *direct* H4 extension to *multi-modal* implicit-SDF, the *killer* feature for v0 v1 chair-side (3D scan + IOS RGB color → 3D crown mesh).

**H5 (Synthetic pretrain + light fine-tune generalizes to real) — STRONGEST DIRECT SUPPORT IN THE READING LIST:** Sonata is *the* paper that *directly* validates H5 in the *strongest possible* way. **(1) Scale evidence: 86.7× more scenes than PC, 14.7× more than MSC, 5.9× more than PPT** (the 3rd strongest H5 paper in the reading list, after 071 TS-MTL's multi-task supervision and 083 PTv3's 7-dataset PPT), with 87% *synthetic* data (Structured3D 21,821 + ASE 100,000 = 121,821 of the 139,769 total). **(2) Data efficiency evidence: 1% scenes → 45.3% Sonata-dec vs 25.8% PTv3-from-scratch, +19.5pp** (the *biggest* data-efficiency gain in the 3D-deep-learning literature, the *direct* answer to "what if we only have 100 clinical scans"). **(3) OOD evidence: AEO 22 scans → 55.9% Sonata-full vs 34.9% PTv3-from-scratch, +21.0pp** (the *biggest* OOD gain in the 3D-deep-learning literature, the *direct* answer to "what if we have a *new* clinic with a *new* scanner"). **(4) Cross-modal evidence: Sonata + DINOv2 = +3.4pp over Sonata alone, +12.8pp over DINOv2 alone** (the *direct* evidence that 2D+3D SSL are *complementary*, the *right* H5 mechanism for v0's *future* multi-modal pre-training with IOS RGB). For v0, the v0 paper's H5 section should be *restructured* around the Sonata paradigm: "pre-train once on 140k+ scenes (3DTeethSeg22 + ToothFairy2 + cTooth + internal clinical scans + synthetic CAD = 50k+ arches), per-clinic linear-probe or 100-shot fine-tune, *exactly* the DINOv2 paradigm", the *direct* v0 v1 product strategy for the 50-100 dental clinics in Korea that need *zero* per-clinic training data. The *87% synthetic* proportion in Sonata is *the* answer to v0's *data scarcity* problem (real clinical scans are *expensive* and *small*, synthetic CAD is *cheap* and *large*, Sonata's H5 result is *direct* evidence that the 87%-synthetic recipe *works*).

## Surprises and interesting things buried in the paper

(1) **"The geometric shortcut is unique to 3D"** is the *single most-quoted* conceptual claim in 3D SSL since PointContrast 2020. The Fig. 2 visualization (CSC collapses to normals, MSC collapses to height, Sonata captures semantics) is the *first* time the 3D-SSL literature has had a *direct visual* of *what* the SSL representations are *actually* learning. The "remove decoder → +39.7pp" ablation is the *largest* single-design-decision contribution in 3D SSL, the *signature* ablation of the paper.

(2) **The decoder is *not* a feature, it's a *bottleneck***: the *U-Net decoder* is the *standard* 3D-perception design (PointNet++ 2017, SparseUNet, PTv1/2/3, *all* use U-Net decoders for segmentation), but Sonata's *encoder-only* design is the *first* paper to *explicitly* remove the decoder during pre-training and *show* that the *resulting* features are *better* for downstream tasks (linear probing +39.7pp, full fine-tune +1.5pp). The *philosophical* implication: the *encoder* is the *right* place to do *self-supervised* learning (it has *diverse* multi-scale features), the *decoder* is *task-specific* and *should be re-trained* for each new task (the *encoder* is the *foundation*, the *decoder* is the *application*).

(3) **The 4.4M-param linear-probe model reaches 72.5% ScanNet mIoU**, the *first* time a 3D SSL method has *matched* the 2D DINOv2 paradigm (linear-probe-without-finetune is a *trustworthy* indicator of representation quality). The *practical* implication: a *frozen* 3D foundation model + a *single* 1×1 conv can be deployed to a *new* clinic with *zero* per-clinic training, the *exact* DINOv2 paradigm for *new* domains.

(4) **The cross-modal 3D+2D result is *new* and *important***: Sonata (pure 3D) + DINOv2 (image lifted to 3D) = 75.91% linear probing (+3.4pp over Sonata alone, +12.8pp over DINOv2 alone), the *first* paper to *explicitly* show that 3D+2D SSL features are *complementary*, not *redundant*. The *practical* implication: the *future* of 3D foundation models is *multi-modal* (3D + image + text), the *direct* template for v0's *future* multi-modal pre-training with IOS RGB color (the *killer* feature for v0 v1 chair-side).

(5) **The OOD +21.0pp AEO result is the *strongest* OOD evidence in the reading list**: Sonata-full on AEO (sparse SLAM, *unseen* data pattern, only 22 training scans) reaches 55.9% mIoU, +20.99pp over PTv3-from-scratch's 34.9%. The *practical* implication: pre-training on *diverse* 3D data (real + synthetic, indoor + outdoor, dense + sparse) is the *correct* H5 mechanism for *any* new 3D domain, *including* the v0 cross-clinic deployment scenario.

(6) **The 87% synthetic data proportion is *bold***: 121,821 of 139,769 scenes are *synthetic* (Structured3D 21,821 + ASE 100,000), the *highest* synthetic proportion of *any* 3D SSL paper. The *result* is *still* the *best* on real-data benchmarks (ScanNet val 79.4% full fine-tune), *direct* evidence that *synthetic* pre-training is *sufficient* for real-data downstream tasks, the *direct* answer to v0's data-scarcity problem (real clinical scans are *expensive* and *small*).

(7) **The feature up-casting is *zero* extra params and *zero* extra inference cost** (2-line PyTorch: `torch.cat([enc1.feat[inv1], enc2.feat[inv2], enc3.feat[inv3], enc4.feat[inv4]], dim=1)`), the *cheapest* multi-scale fusion in 3D deep learning, the *direct* mechanism for v0 sub-task 1 to *add* multi-scale context without *any* computational overhead.

(8) **The 1% data result is the *killer* v0 H5 evidence**: Sonata-decoder-probe at 1% scenes (≈ 16 scenes out of 1613) reaches 44.5% mIoU, +19.5pp over PTv3-from-scratch's 25.8% on the *same* 16 scenes. The *practical* implication: a v0 deployment with *only* 100 clinical scans can reach 45% TIR on sub-task 1 with Sonata-style pre-training, *the* key to v0 v1 product viability (50-100 clinics, *no* need for *thousands* of scans per clinic).

(9) **The progressive parameter scheduler is *the* novel training trick**: mask size 10→40 cm, mask ratio 30→70%, teacher temperature 0.04→0.07, weight decay 0.04→0.2 over the *first 5%* of training, the *first* paper to *systematically* explore *all four* scheduler parameters simultaneously, the *philosophical* complement to the *fixed* scheduler paradigm in PC/MSC/CSC/PPT.

(10) **The "remove decoder" + "feature up-casting" is the *architectural* insight** that the *entire* 3D SSL literature has been *missing*: the *decoder* is the *primary* source of the geometric shortcut (it re-introduces point-level features at the *original* resolution, where the spatial information is *most* accessible), and *removing* it *forces* the loss to operate on *coarser* features (where the spatial information is *globally* mixed). The *up-casting* recovers the *multi-scale* information *without* the geometric shortcut risk. The *net* result: a *smaller* model (encoder-only), a *faster* training (no decoder forward pass), a *better* linear probing (+39.7pp), and a *better* full fine-tune (+1.5pp). The *next* paper that *combines* Sonata with *cross-tooth attention* (paper 045 TSegFormer-style) is the *direct* v0 sub-task 1 paper.

(11) **The "no LayerNorm" design is *counter-intuitive* but *correct***: the *default* PTv3 uses LayerNorm in attention and BatchNorm in pooling (the *standard* 2017-2024 Transformer design), but Sonata uses *no* normalization (the *BatchNorm* in pooling is *implicit* in the pooling operation). The *motivation*: LayerNorm *requires* per-point batch statistics, which *break* the multi-dataset joint training paradigm (different datasets have different mean/std). The *trade-off*: -1-2pp from-scratch accuracy, +5-7pp SSL pre-training benefit. The *practical* implication: the *next* paper that *combines* Sonata with *cross-tooth* and *cross-arch* attention (paper 045 TSegFormer-style + paper 046 ToothGroupNet-style) is the *direct* v0 sub-task 1 paper, *if* the *no-LN* design is *validated* on dental data.

(12) **The 86.7× data scale-up is the *single largest* in the 3D SSL literature**: 139,769 scenes (vs PC's 1,613, MSC's 6,660, PPT's 23,706), the *enabling* evidence for v0's H5 deployment (v0 v1 can mix 3DTeethSeg22 + ToothFairy2 + cTooth + clinical-internal + synthetic CAD = 5k-50k "scenes" if each arch is treated as a "scene", and pre-train the v0 sub-task 1 encoder with the Sonata recipe for 1-2 weeks at ~$200-500 Lambda).

(13) **The Sonata-pretrained encoder can be *plugged into* any 3D pipeline** (latent-diffusion, implicit-SDF, mesh generation, *all* the v0 sub-tasks), the *first* paper to *explicitly* demonstrate this *plug-and-play* property. The *practical* implication: v0 v1 can pre-train the *encoder once* on the 50k-arch dataset, and *reuse* the *same* encoder for *all* 5 sub-tasks (1: tooth instance seg, 2: prep crown generation, 3: opposing crown generation, 4: occlusion refinement, 5: mesh output), the *single* highest-leverage addition from the entire 84-paper reading list for the v0 v1 product.

(14) **The 7-dataset joint pre-training is the *direct* template for v0's *cross-clinic* pre-training**: Sonata uses *all 7 major* 3D perception datasets jointly, the *first* paper to *demonstrate* that *cross-domain* (indoor + outdoor, real + synthetic, dense + sparse) joint pre-training *uniformly improves* all downstream tasks. For v0, the v0 paper's H5 section should *cite* this as the *direct* mechanism: "v0 sub-task 1 pre-training on 3DTeethSeg22 + ToothFairy2 + cTooth + clinical-internal + synthetic CAD, *exactly* the Sonata multi-dataset paradigm".

(15) **The Sonata codebase is *production-ready* and *Apache-2.0***: github.com/facebookresearch/sonata with pre-trained weights on HuggingFace (facebook/sonata), FlashAttention-compatible, PyTorch 2.5.0 + CUDA 12.4, conda env file provided. The *practical* implication: v0 v1 can *directly* use the *pre-trained* Sonata encoder for *zero-cost* pre-training, *bypassing* the 3-day 8×A100 pre-training entirely (the *single highest-leverage* addition from this paper: *use the released weights*).
