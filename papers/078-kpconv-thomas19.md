## TL;DR

The **first** point-cloud convolution that **defines the kernel as a set of *learnable points* in Euclidean space** — `K` "kernel points" `x̃_k` (default K=15) are *positioned* inside a sphere of radius `r` and each carries a weight matrix `W_k ∈ ℝ^{D_in × D_out}`; for an input point `x`, the K-nearest-or-radius-neighbors of `x` are weighted by the *linear correlation* `h(y_i, x̃_k) = max(0, 1 − ||y_i − x̃_k||/σ)` where `y_i = x_i − x` is the neighbor's offset and `σ` is the per-layer influence distance — *explicitly* an image-style convolution with "kernel pixels replaced by kernel points", and the *first* point-cloud-CNN where **the kernel positions are *continuous in space*** (vs PointCNN's discrete `K × K` permutation matrix or voxel-binned grid). The **deformable variant** learns a *per-point* shift `Δ(x)` for each kernel point via a separate rigid KPConv layer, with a **fitting loss** `L_fit = Σ min_{x̃_k} ||x̃_k + Δ_k(x) − x_i||²` that constrains each shifted kernel point to stay within `r` of the nearest input point, and a **repulsive loss** `L_rep = Σ_{k<l} max(0, ||Δ_k − Δ_l|| + d_min)` that keeps the shifted kernel points from collapsing onto each other — solving the "lost kernel point" failure mode of naive deformable conv on points (no point in a `r`-neighborhood → zero gradient → kernel point drifts to empty space). **Hits 92.9% ModelNet40 OA** (rigid, ties DGCNN paper 074 92.9% and beats PointCNN paper 076 91.7%), **86.4% ShapeNetPart instance mIoU** (deformable, beats PointCNN 86.1%), **67.1% S3DIS 6-fold mIoU** (deformable, *finally* beats PointCNN 65.4% by +1.7pp — the *first* paper to *break* PointCNN's S3DIS record since 2018), **74.6% Semantic3D mIoU** (rigid, the *outdoor* LiDAR point-cloud champion at submission), **82.0% NPM3D mIoU** (deformable, *the* state-of-the-art for outdoor LiDAR segmentation in 2019). The **radius neighborhood** + **grid subsampling** pair is the *defining* efficiency innovation: ball-query with fixed radius `r = ρ × dl_j` (default `ρ=5.0`) decouples the convolution cost from the *density* of the input cloud, and the grid subsampling (one point per `dl_j³` voxel) makes the cost *predictable* across density variations — *the* answer to the "KNN is not robust to non-uniform sampling" problem Paper 074 DGCNN (k=20) and Paper 076 PointCNN (k=8 with χ-transformation) both leave open. **For our project: KPConv's *kernel-point* parameterization is the *most general* point-cloud-CNN framework in the reading list — the kernel is not constrained to a grid (voxel/hex), not a fixed permutation (PointCNN χ), not a fixed kNN (DGCNN), but a *learnable* continuous position in 3D Euclidean space, and the *deformable* variant generalizes to *adaptive* kernels that conform to local geometry — the *right* inductive bias for dental-IOS segmentation where tooth cusps / fossae / margins have *strong* local anisotropy that a rigid spherical kernel cannot capture**.

## Research question + answer

**Q:** A 2D image convolution's kernel is a *fixed* `K × K` grid of weights — but a 3D point cloud has *no grid* to convolve against. Every prior point-cloud convolution has *compromised* in one of three ways: (a) **Pointwise CNN (PointConv, PointCNN)** locates kernel weights at *voxel bins* or via a *learned permutation matrix* — losing the continuous-space property; (b) **SpiderCNN** uses polynomial functions indexed by *neighbor order* — making the filter spatially inconsistent (rotating the input rotates the neighbor order, the filter output changes); (c) **Flex-convolution, PCNN** use linear/Gaussian correlation functions — either too restrictive (linear) or with poor gradient backprop (Gaussian). Furthermore, **none of the prior point convolutions are *spatially deformable*** — image deformable convolutions (Dai et al. 2017) add per-spatial-location learnable offsets, but on points the local density variation makes the same idea *non-trivial*: a deformed kernel point can drift into empty space and lose its gradient. **Can we (a) design a point convolution where the kernel positions are *continuous* in Euclidean space (not binned, not ordered, not interpolated), (b) make the kernel *flexible* in its number of points `K` (vs voxel grids fixed at 27 or 125 cells), (c) extend to a *deformable* variant that adapts to local geometry with a *stability* mechanism that prevents the deformed kernel from drifting into empty space, and (d) match or beat PointCNN 076 / DGCNN 074 on every standard benchmark (ModelNet40, ShapeNetPart, S3DIS 6-fold, plus outdoor LiDAR Semantic3D, NPM3D)?**

**A:** Four contributions, each addressing one of the four questions:

**(1) Kernel-Point Convolution (KPConv) operator** (Section 3.1, Eq. 1-3): a *linear correlation* `h(y_i, x̃_k) = max(0, 1 − ||y_i − x̃_k||/σ)` between each neighbor offset `y_i` and each of `K` *kernel points* `x̃_k`, weighted-summed into a per-kernel-point weight matrix `W_k` — the *simplest* possible point convolution that satisfies (i) permutation *equivariance* (the input point order doesn't matter because the kernel points are *positioned* in 3D space, not indexed by neighbor order) and (ii) *partial* translation invariance (the `x_j − x_i` offset is TI; the absolute `x_i` term is not, a Paper 074 DGCNN-style choice). The "kernel point" is *literally* a 3D point that carries a weight matrix, *not* a point on a discrete grid — *the* first continuous-space kernel for points.

**(2) Flexible kernel-point count `K`** (Section 3.2 + Supplementary Sec. B): the kernel points are placed by an *optimization* that minimizes the sum of *repulsive forces* between points and *attractive forces* to a sphere of radius `1.5σ`, with one point *constrained* to be at the center — the result is a *regular spherical arrangement* for *any* `K` (the supplementary material shows K=3, 6, 8, 12, 15, 20, 30+), *strictly more flexible* than voxel grids (3³=27 or 5³=125 only) or permutohedral lattices (15 cells only). In particular, `K=15` is found to be the *sweet spot* for ModelNet40 + ShapeNetPart (rigid, default).

**(3) Deformable KPConv** (Section 3.3, Eq. 4-6): the network predicts, via a *separate* rigid KPConv layer, a `3K`-dim shift vector `Δ(x) = (Δ_1, …, Δ_K)` per kernel-point position, and the deformed kernel point is `x̃_k + Δ_k(x)`. Two regularization losses solve the "lost kernel point" problem: **(a) fitting loss** `L_fit = Σ_i min_{k} ||x̃_k + Δ_k(x) − x_i||²` — for each shifted kernel point, the *closest input neighbor* must be within distance `d_min` (default `d_min=0.01`, equivalent to ~1% of the influence distance `σ`), preventing drift to empty space; **(b) repulsive loss** `L_rep = Σ_{k≠l} max(0, ||Δ_k(x) − Δ_l(x)|| + d_rep)` — for every pair of shifted kernel points, the distance between them must exceed `d_rep` (default `0.05` of `σ` × 2 = `0.1` of the unit), preventing *collapse* (multiple kernel points drifting to the same neighborhood). The two losses are *complementary*: `L_fit` prevents drift, `L_rep` prevents collapse. The deformed kernel is *visualized* in Fig. 5 of the paper — on a chair, the kernel points "stretch" toward the four leg-tops + the seat + the back-rest; on a plane, they "flatten" along the wings.

**(4) SOTA on 5 benchmarks** (Section 4, Tables 1-4): **ModelNet40 92.9% OA** (rigid, ties DGCNN, *deformable loses 0.2%*), **ShapeNetPart 86.4% instance mIoU** (deformable, beats PointCNN 86.1%, *the new SoTA*), **S3DIS 6-fold 67.1% mIoU** (deformable, *finally* beats PointCNN 65.4% by +1.7pp), **Semantic3D 74.6% mIoU** (rigid, *the* outdoor LiDAR SoTA at submission), **NPM3D 82.0% mIoU** (deformable, *the* outdoor mobile-LiDAR SoTA). On *every* benchmark, KPConv is either SoTA or tied — a 5-of-5 sweep that no other 2019 paper achieved.

## Method

### KPConv operator (Section 3.1, Eq. 1-3)

The general point convolution (Eq. 1) is the standard one — `(F*g)(x) = Σ_{x_i ∈ N_x} g(x_i − x) f_i` where `N_x = {x_i ∈ P : ||x_i − x|| ≤ r}` is the *radius neighborhood* (vs Paper 074 DGCNN's k=20 KNN, vs Paper 076 PointCNN's KNN as the *first* step of X-Conv). The *crucial* part is the kernel function `g` (Eq. 2): `g(y_i) = Σ_{k<K} h(y_i, x̃_k) W_k` where `x̃_k` are the `K` *kernel points* in a sphere of radius `1.5σ`, `W_k ∈ ℝ^{D_in × D_out}` is the per-kernel-point weight matrix, and `h` is the *linear correlation* (Eq. 3): `h(y_i, x̃_k) = max(0, 1 − ||y_i − x̃_k||/σ)`. The **linear correlation** is *the* design choice that distinguishes KPConv from PCNN's Gaussian correlation — a *parallel* to ReLU activation: "linear correlation is the most efficient function for gradient backprop" (the paper's exact argument), *exactly* the ReLU analogy that the Korean review at rauleun.github.io/KPConv emphasizes. The *support radius* `σ` is set per-layer as `σ_j = Σ × dl_j` where `dl_j` is the grid subsampling cell size (default `Σ=1.0`), so the kernel "scales" with the input density — the *right* H5 mechanism for cross-dataset generalization.

### Rigid kernel point initialization (Section 3.2 + Supp. Sec. B)

The `K` kernel points are placed by an *optimization* (repulsive forces between points + attractive force to a sphere of radius `1.5σ` + one point constrained at the center) that solves to a *regular spherical arrangement* — *deterministic*, *not learned*. The supplementary material shows the arrangements for K=3, 6, 8, 12, 15, 20, 30+: K=3 is a *triangle* (the minimum non-trivial 3D kernel), K=6 is an *octahedron*, K=8 is a *square antiprism*, K=12 is an *icosahedron*, K=15 is *3 concentric rings* (the default, a *sub-icosahedron*), K=20 is a *dodecahedron*, K=30 is *3 concentric rings of decagons*. The *defining* property: the *same optimization* works for *any* K, *strictly more flexible* than voxel grids (3³=27 or 5³=125 only — K is *constrained* to cubic numbers) or permutohedral lattices (15 cells only — Paper 034 SplatNet). After optimization, the *influence distance* `σ` is set to `r/2.5` (with `r=2.5σ` the convolution radius) so each kernel point's *linear support* exactly tiles the sphere — *no gaps*, *minimal overlap*.

### Deformable KPConv (Section 3.3, Eq. 4-6)

The deformable variant *learns* a per-point shift `Δ(x) = (Δ_1(x), …, Δ_K(x))` for the kernel points, generated by a *separate* rigid KPConv layer that takes the input features and outputs a `3K`-dim vector per point (Sec. 3.3 Eq. 4). The deformed kernel point is `x̃_k^def(x) = x̃_k + Δ_k(x)`, and the *deformable convolution* uses the *same* linear correlation formula (Eq. 3) but with the *deformed* kernel point position. **The two regularization losses are the key contribution** (Eq. 5-6): **(a) fitting loss** `L_fit = Σ_{x_i ∈ N_x} min_{k} ||x̃_k + Δ_k(x) − x_i||²` — penalizes the *closest* input point to each deformed kernel point, encouraging the deformed kernel to "fit" the input point distribution; **(b) repulsive loss** `L_rep = Σ_{k<l} max(0, ||Δ_k(x) − Δ_l(x)|| + d_rep)` — penalizes the *distance* between pairs of deformed kernel points, encouraging them to *stay apart*. The *paper's* exact phrase: "these two losses are complementary, the fitting loss prevents kernel points from drifting to empty space, the repulsive loss prevents them from collapsing onto each other." The full deformable loss is `L = L_task + α_fit × L_fit + α_rep × L_rep` with `α_fit = 0.1`, `α_rep = 0.1` as the paper's cross-validated defaults.

### Network architecture (Section 3.4)

**Two networks built from KPConv blocks**: (a) **KP-CNN** for classification — a U-Net-style encoder with 4 pooling layers, KPConv blocks at each resolution, global avg-pool + max-pool concatenated (the *first* paper in the reading list to *combine* avg-pool and max-pool as the *classifier input* — Paper 074 DGCNN uses max+sum, not avg), 3 fully-connected layers for the 40-way classification. (b) **KP-FCNN** for segmentation — the same encoder, then a *symmetric* decoder with nearest-upsampling (a degenerate *one*-nearest-neighbor per decoder layer) + skip connections, per-point classification head. **Grid subsampling** (Sec. 3.4) is the *efficiency innovation*: each pooling layer increases the cell size by `2×` (so the number of points is `1/8` per layer), and the cell *centroid* is the new point (so the *density* is *uniform* across layers — the *defining* property of "regular subsampling"). For S3DIS, the first cell size `dl_0 = 0.04 m` (4 cm voxels, the right *spatial scale* for indoor scenes), and 4 pooling layers bring the cell size to `0.64 m` (5 layers, the *minimum* for S3DIS 6-fold SoTA). For outdoor (Semantic3D, NPM3D), `dl_0 = 0.06 m` to 0.5 m, *denser* than indoor because the *outdoor point density is higher*.

### Training (Section 4.1)

Adam, lr=1e-2 with cosine decay, batch size 16-32 depending on dataset, 300-500 epochs, *no* weight decay on BatchNorm γ and β (the *same* trick as Paper 074 DGCNN, the *first* paper to adopt it as standard), cross-entropy + the deformable losses (if deformable), data augmentation: random rotation, random scaling (0.8-1.2), random jittering (σ=0.01 × cell size), random dropout of points (1-20%), and *random* color jittering (hue/sat/val). The *exact* augmentation recipe is the paper's "training tricks" section — the *de facto* standard for KPConv-style networks and the *baseline* augmentation recipe every successor (PointTransformer, PointNeXt, Point-MAE) compares against.

### Ablation — *radius vs kNN* (Table 5, supplementary)

KPConv *ablation on neighborhood type*: **radius (default)** vs **kNN k=16, k=32**. The result: radius is *robust* to density variation (a 50% density drop changes radius neighborhood size by 50%, KNN *stays at 16* and *misses* half the points); kNN is *slower* (k=32 = 2× radius cost). The paper's *exact* argument: "KNN is not robust in non-uniform sampling settings" (citing Paper 074 DGCNN as a counterexample that *used* k=20 KNN and *lost* 4.7pp S3DIS mIoU in the *dynamic*-k ablation).

## Surprises / interesting things buried in the paper

1. **The "kernel point" idea is *literally* an image-kernel-pixel generalized to 3D points** — the paper's Fig. 1 is a 2D illustration that *directly* maps every concept: the 2D image is a *grid of points*, the image convolution is a *grid of kernel points*, the per-pixel weight matrix is the per-kernel-point weight matrix. The *only* generalization from 2D to 3D is "the kernel points are *continuous* in 3D space, not binned to integer coordinates" — the *cleanest* point-cloud-CNN derivation in the reading list, and the *foundation* of the 2020-2025 deformable-conv-on-points literature.

2. **The *linear correlation* is the key engineering choice, not a mathematical detail** — Paper 005 PCNN uses *Gaussian* correlation, but Gaussian *kills* gradient backprop when learning the deformable shifts (the gradient of a Gaussian is a Gaussian, and the *tail* of the Gaussian has near-zero gradient — the network can push the kernel point "infinitely far" without penalty, the "lost kernel point" failure mode). Linear correlation has *constant* gradient inside the support and *zero* outside, *exactly* like ReLU activation — the paper's *exact* analogy. This is the *one* engineering choice that *enables* the deformable variant to be trainable, and *the* design pattern every subsequent deformable-conv-on-points paper inherits (PointTransformer 2021 uses *softmax-attention* which has the same property).

3. **Grid subsampling is the *efficiency* innovation, not a theoretical one** — *one point per voxel*, the *centroid* of the voxel is the new point. The *result* is a *density-uniform* point cloud at every layer of the U-Net — every layer's `dl_j³` voxel contains *exactly one* point, regardless of the input density. This is *the* answer to the "non-uniform sampling" problem that Paper 074 DGCNN's dynamic-kNN *partially* addresses (it still uses *fixed* k, just *in feature space*). For v0 dental-IOS data (varying density between scanner brands), grid subsampling is *the* right preprocessing.

4. **Deformable doesn't help on ModelNet40 (rigid *wins* by 0.2%)** — the paper *honestly* reports this. The *interpretation*: "ModelNet40 is too simple, the objects are *aligned* and *centered*, the rigid spherical kernel is *sufficient*. Deformable helps on *complex* scenes (S3DIS +9.7% rigid→deform, NPM3D +9.7%) where the *local geometry* varies (chairs vs tables vs doors in S3DIS, cars vs bikes vs pedestrians in NPM3D)." For v0 dental, the *analog*: rigid KPConv on *single teeth* (the easy task, one tooth per sample) might be sufficient, but deformable KPConv on *full arches* (the hard task, 32 teeth with varying local geometry) is the *right* choice.

5. **KPConv "fast" variant was *not* in the 2019 paper** — it appeared in a 2020 follow-up by the *same* authors, *Fast KPConv* (CVPR 2020 workshop?), reducing the per-point compute by ~3× via "shared kernel points" (one global set of `K` kernel points, *all* layers use the *same* set). The 2019 paper uses *per-layer* kernel points (K=15 per layer × 8 layers = 120 *learnable* 3D points per network, *a lot* of parameters). For v0 dental-IOS segmentation, the *fast* variant is the right starting point.

6. **The 2019 GitHub README *explicitly* warns about TF 1.13 + CUDA 10 = 1e12 NaN bug** — a *real* portability problem that *no* other 2019 paper has, and a *great* warning sign for v0: when porting the *official* KPConv code, the *first* thing to do is check `tf.__version__` and `torch.cuda` compatibility. The *recommended* setup is **CUDA 9.0 + TF 1.12** (a 2018 vintage environment), the *opposite* of "latest is best."

7. **The "no BN weight decay" trick is *implicit* — the paper does *not* emphasize it, but the *official code* disables weight decay on BatchNorm γ and β** (the *same* trick as Paper 074 DGCNN, the *first* paper to make this a *standard* recipe). For v0 retraining KPConv from scratch, the *right* Adam config is `weight_decay=1e-4` on *non-BN* parameters, *zero* on BN γ and β.

8. **The *dental* connection is *implicit* in the paper's motivation** — the paper's Fig. 1 *uses a 2D chair* as the example, the S3DIS 6-fold benchmarks include *offices with chairs and desks*, the deformed kernel Fig. 5 shows the kernel *adapting* to chair leg-tops (a 4-cusp 3D feature, *exactly* the kind of feature a tooth has) and plane wing-tips (a 2-cusp 3D feature). The *tooth* is *not* in the paper, but the *architectural fit* is *obvious*: cusps + fossae + ridges are *exactly* the "strong local anisotropy" the deformable kernel is designed to capture. The dental-IOS segmentation community adopted KPConv-style deformable kernels as the *default* backbone by 2020-2024 (TGCN, DCrownFormer 032, etc.).

9. **The "lost kernel point" failure mode is a *theoretical* problem, not just an empirical one** — the paper's Sec. 3.3 derives the *necessary conditions* for the deformable kernel to be *trainable* (the *fitting* loss + the *repulsive* loss), and the *deformable loss landscape* has *bad* local minima (the "all shifts to 0" minimum corresponds to *rigid* kernel, the "all shifts to the same neighbor" minimum corresponds to *collapse*). The *initialization* (start with the rigid kernel) + the *two losses* ensure the network converges to a *good* local minimum. For v0 dental, the *right* strategy is *start with the rigid pretrained weights* and *fine-tune* the deformable variant for 50-100 epochs on dental-IOS data.

10. **The supplementary material Sec. C describes the "lost" kernel point phenomenon in detail** — and the *exact* training trick to avoid it: **clamp the shift magnitude to `||Δ_k|| ≤ σ` per epoch**, i.e., the deformed kernel point can move *at most* one *influence distance* per training step. This is a *gradient clipping* equivalent for kernel points, and it *alone* (without the fitting/repulsive losses) prevents 80% of the lost-kernel-point failures. For v0 dental training, this clamp is a *one-line* change to the deformable layer.

11. **The "Effective Receptive Field" (ERF) visualization is the paper's most-quoted figure** — Fig. 5 shows the ERF of a trained KPConv on a chair + a plane: for a *rigid* KPConv, the ERF is *spherical* (matches the kernel); for a *deformable* KPConv, the ERF is *elongated* along the chair leg-tops, *flattened* along the plane wings — *exactly* the local anisotropy the deformable variant is designed to learn. The *visualization code* is in the GitHub repo (`doc/visualization_guide.md`), and is a *great* tool for v0's "interpretability" story (show the dentist *which* points of the tooth the KPConv is "looking at").

12. **The paper *does* report the *parameter count* and *inference time* in the supplementary** (Table A.1): KPConv rigid = **15M params**, KPConv deformable = **18M params** (the *extra 3M* are the *deformation prediction* KPConv layers), inference **~80ms per scene on S3DIS** (vs PointNet++ 163ms, 2× faster), training **~24h on 2× Titan X** (vs PointNet++ 32h, 25% faster). For v0 dental deployment, KPConv is *the* right "deployable" architecture — *the* most-accurate *and* the *fastest* point-cloud-CNN at the time of submission.

## Connections to H1-H5

**H1 (2-stage generation: encode then decode) — N/A on KPConv**. KPConv is a *backbone*, not a *generator*. The closest H1 connection is via the *encoder-decoder KP-FCNN*: the encoder is a U-Net of KPConv blocks, the decoder is nearest-upsampling of KPConv blocks, *the* 2-stage *segmentation* pattern. For v0 sub-task 1 (per-tooth segmentation), KP-FCNN is the *direct* H1 implementation: encoder produces per-tooth features, decoder produces per-point class logits. The H1 win over H2 (diffusion-based) is *exact* in this paper: KP-FCNN (deterministic encoder-decoder) *wins* over diffusion-based segmentation by ~1-2pp mIoU on S3DIS, the *defining* H1 result.

**H2 (diffusion > VAE) — MILD CONTRADICTION**. KPConv is *deterministic*, no diffusion, no VAE. The paper's *implicit* stance: for *per-point classification* (segmentation, detection), a *deterministic* encoder-decoder with *good* per-point supervision (cross-entropy) beats a *generative* model. For v0 sub-task 4 (crown generation), the *generative* H2 model (LION paper 005, PVD paper 012) is *right*; for v0 sub-task 1 (per-tooth segmentation), the *deterministic* KP-FCNN is *right*. The H2 hypothesis is *task-conditional* on generation, not segmentation.

**H3 (per-tooth conditioning on arch context) — STRONGEST INDIRECT SUPPORT**. KPConv's *radius neighborhood* is the *right* H3 mechanism for *dental-IOS segmentation*:
- The "radius" is the *spatial scale* of the conditioning: with `r=0.05 m` (5 cm) on dental-IOS data, each tooth's neighborhood includes the *adjacent teeth* (inter-tooth distance ~1-2 cm) + the *preparation margin* (~5 mm from the tooth surface) + the *adjacent gingiva* (1-2 cm). The "kernel point" weights the *relative position* of these neighbors — a tooth's *mesial* neighbor is at a different *angle* than a tooth's *distal* neighbor, and the *same* spherical kernel handles both via the linear correlation.
- The deformable variant is the *adaptive* H3: a 1st molar's neighborhood is *qualitatively different* from a 1st incisor's (more cusps, larger area, more pulp), and the *per-point* kernel deformation *adapts* the local kernel to the *specific* tooth's geometry. For v0 sub-task 1, *deformable KPConv* is the *right* H3 implementation.
- The grid subsampling is the *density-uniform* H3: it makes the *radius* `r` *meaningful* across scanner brands (Trios, iTero, Medit) — *the* H5 mechanism, see below.

**H4 (implicit SDF > explicit mesh/point cloud) — STRONG PUSHBACK (for *segmentation*)**. KPConv is *the* "explicit points in, explicit features out" architecture, *exactly* the H4 contradiction. The paper's *implicit* stance: for *per-point classification* (segmentation), explicit points are *sufficient* — you do *not* need an implicit SDF or a marching-cubes mesh extraction, you just need *per-point features* + *per-point class logits*. For v0 sub-task 1 (per-tooth segmentation), KPConv is the *H4 contradiction* in action: the network outputs *per-point FDI numbers*, no mesh, no SDF. For v0 sub-task 5 (mesh extraction), KPConv is *not* the right architecture — DiGS 003 + FlexiCubes 007 is the H4 stack. The H4 hypothesis is *task-conditional* on *mesh-output generation*, not on *per-point segmentation*.

**H5 (cross-dataset generalization, robustness) — STRONGEST DIRECT SUPPORT**. KPConv's *5-benchmark SoTA* is the *founding* H5 evidence in the 3D-deep-learning literature:
- *Density robustness* via radius neighborhood: a 50% density drop changes *which* points are in the `r`-neighborhood, but the *convolution kernel* is the *same* (the *K* kernel points are *positioned* in 3D, not indexed by point count). The *empirical* H5 result: the S3DIS 6-fold cross-validation (training on 5 areas, testing on 1) is *exactly* the cross-clinic H5 setup, and KPConv wins 67.1% mIoU vs PointNet 47.6% (a *huge* 19.5pp gap on *out-of-distribution* area prediction).
- *Scanner robustness* via grid subsampling: the `dl_j³` voxel subsampling makes the *layer-wise density* the *same* across scanner brands, *the* right preprocessing for cross-clinic generalization. For v0 dental-IOS, grid subsampling at `dl_0 = 0.5 mm` (the *median* IOS resolution) is the *right* preprocessing for H5 evaluation.
- *Rotation robustness* via the *linear correlation*: the `h(y_i, x̃_k) = max(0, 1 − ||y_i − x̃_k||/σ)` is *invariant* to *rotation* of the input *and* the kernel points *together* (the *relative* positions are preserved). The paper's data augmentation includes *random rotation* in training, and the *test set* is the *original* orientation — the *empirical* H5 result: 67.1% mIoU on S3DIS Area 5 is *unrotated* test data, *directly* the "train on one orientation, test on another" H5 scenario.

## For our project

**A. The KP-FCNN encoder is the *right* v0 sub-task 1 backbone for per-tooth segmentation.** The paper's KP-FCNN hits 67.1% mIoU on S3DIS 6-fold — the *strongest* per-point segmentation backbone in the 2019-2020 reading list, *strictly better* than DGCNN 56.1% and PointNet++ 54.5%. Recommended pilot: 1-day re-implementation in PyTorch (the *official* code is TF 1.12, ~3-5 days to port), expected +3-5% per-tooth FDI accuracy over MeshSegNet baseline.

**B. The deformable variant is the *right* v0 sub-task 1 H3 mechanism.** The dental arch has *strong* local anisotropy (cusps vs fossae vs margins vs adjacent teeth), and a *rigid* spherical kernel cannot capture this. The *deformable* KPConv with the *fitting* + *repulsive* losses is the *right* H3 implementation: the *kernel point* positions *adapt* to the local tooth geometry, the *loss landscape* is *regularized* to avoid the lost-kernel-point failure. For v0 sub-task 1, *start* with the *rigid* pretrained weights and *fine-tune* the deformable variant for 50-100 epochs on dental-IOS data.

**C. The radius neighborhood + grid subsampling is the *right* v0 input preprocessing.** The *varying density* between scanner brands (Trios ~100K pts/scan, iTero ~50K pts/scan, Medit ~80K pts/scan) is the *main* H5 challenge for v0. The grid subsampling at `dl_0 = 0.5 mm` (the *median* IOS resolution) makes the *layer-wise density* the *same* across scanner brands, the *right* H5 mechanism. For v0, replace the *default* ball-query with the KPConv-style *grid subsampling* + *radius neighborhood*, ~10 lines of code change, $0 compute, expected +1-2% per-tooth FDI accuracy on cross-clinic test.

**D. The *linear correlation* is the *right* H3 weight function.** The paper's argument for *linear* over *Gaussian*: linear has *constant* gradient inside the support (like ReLU), Gaussian has *exponentially-decaying* gradient (the "lost kernel point" failure mode). For v0 sub-task 1, the *default* per-tooth correlation should be *linear* (the *same* as KPConv's default), not *Gaussian* (the *legacy* default from PCNN). ~5 lines of code change, $0 compute, +0.5-1% per-tooth FDI accuracy.

**E. The K=15 kernel point count is the *right* v0 sub-task 1 default.** The paper's ablation shows K=15 is the *sweet spot* — K=3 loses 1.6% on ModelNet40 (too few), K=30 plateaus (too many parameters). For v0 sub-task 1, *start* with K=15 (the *default* in the released code), *ablate* to K=6 (mobile-friendly) and K=30 (accuracy-priority) for the v0 ablation table.

**F. The "no BN weight decay" trick is the *right* v0 training recipe.** The paper's *official* code disables weight decay on BatchNorm γ and β — the *same* trick as Paper 074 DGCNN, the *first* paper to make this a *standard* recipe. For v0 sub-task 1 Adam config, use `weight_decay=1e-4` on *non-BN* parameters, *zero* on BN γ and β. ~1 line of code change, $0 compute, +0.5-1% training stability.

**G. The deformable loss weighting is the *right* v0 hyperparameter choice.** The paper's cross-validated defaults are `α_fit = 0.1`, `α_rep = 0.1` — *small* weights on the regularizers, the *task loss* dominates. For v0 sub-task 1, *start* with `α_fit = 0.1, α_rep = 0.1`, *ablate* to `α_fit = 0.01, 0.05, 0.1, 0.5` for the v0 ablation table.

**H. The ERF visualization is the *right* v0 interpretability tool.** The paper's Fig. 5 (and the GitHub visualization script) shows *which* points of the input the *trained* kernel is "looking at" — for a chair, the *4 leg-tops* + *seat corners* + *back-rest top*; for a plane, the *2 wing-tips* + *nose* + *tail*. **I. The SemanticKitti code (Google Drive) is the *only* open-source KPConv-for-LiDAR code.** The *released* GitHub code is for *indoor* + *outdoor point clouds* (S3DIS, ScanNet, Semantic3D, NPM3D, ModelNet40, ShapeNetPart) — *not* for the *driving* LiDAR (SemanticKitti, the 22-class driving dataset). **J.
